# Run gold and shop

Current structure map; implementation reference, not a contract.

## Melta regional shop discount

- Melta affection >=1 adds 10 percentage points to `MerchantNPC`'s effective affection discount only for active-run gold shops whose scene matches the current `slime` route. The global RunModifierService snapshot is not changed by this local benefit, so other-area and Hub shops keep their own discounts.
- Current Sasha-wide 5% + Melta 10% becomes 15% off the original price; a later Sasha 10% would combine to 20%. `MerchantShopPolicy` clamps the combined rate, and `MerchantOfferPricing` retains the separate special-offer multiplier and final rounding. Item price tags and purchases continue reading the same `entry.price`.
- The merchant subscribes to affection changes and reprices its existing stock when Melta changes. It retries late manager binding and removes the subscription on disable. Original prices, offer identity and sold state are preserved by the existing stock path; no new regional field is saved. [Approved scope](../ActiveTasks/chloe-melta-affection-rewards.md).

## Ownership and lifecycle

GamePlayData.runGold owns the current run balance. Existing CurrencyManager exposes GetGold/AddGold/SpendGold and OnGoldChanged. RunSessionLifecycleService resets gold at start, end and development reset; inactive runs expose zero. Sasha's second permanent reward adds a profile-owned `GameData.retainedRunGold` credit: run-end commit captures min(held gold, 500) on Defeat/TimeOver, then GamePlayDataManager.StartRun consumes and flushes that credit before assigning the new run balance and firing OnRunStarted. Repeated active StartRun calls do not consume/reset again. Victory/Abort produce no new credit. Old profile JSON defaults the additive credit to zero. Gold remains separate from persistent magic stones. No new singleton or bootstrap object was introduced.

## Drop and HUD flow

ExperienceRewardSource uses its existing valid death-reward gate, so suppressed rewards also suppress gold. For procedural room encounters, MonsterSpawnRoomGroup assigns an exact runtime gold share to every planned spawn before combat. Normal Combat rooms carry 120 gold and Large Combat rooms carry 180 gold; shares are weighted by each monster prefab's base experience and sum to the room budget. Non-Combat room waves are explicitly assigned zero so event/treasure-authored monsters cannot fall back to uncapped rewards. AlarmBellInteractable owns a separate 50-gold encounter budget, spread across its planned spawns. Summoned units that already suppress experience continue to suppress gold.

Unconfigured/legacy ExperienceRewardSource users retain the fallback of clamp(baseExperience * 6, 40, 600), followed by a uniform integer roll within ±15% (ceil lower/floor upper). All paths still spawn the existing GoldPickup2D from GoldPickup.prefab and split the total across at most eight pickups. Pickup scatter and reward amounts are unchanged. GoldPickup2D and ExperiencePickup2D now wait on the ground during combat, then rise and converge on the player together; see the combat collection section below. They have no trigger callback or required Collider2D; existing authored colliders do not control collection. Collection marks the pickup consumed before reward callbacks to prevent duplicate grants. Nineteen monster prefabs reference the pickup.

Art/Sprites/Items/gold.png is the supplied image, imported as a point-filtered 16 PPU sprite. GlobalUIRoot contains an authored GoldUI row above the magic-stone row. CurrencyUI.showRunGold selects the balance and event; the UI owns no currency state. During an active run the row shows the current run balance. Outside a run (including the lobby), it projects the profile's nonnegative retainedRunGold credit, not the zero spendable run balance. Run-end currency events and initial display both use this projection. Gold rows additionally refresh on GameDataStore.OnDataLoaded and unsubscribe on destruction. The UI never consumes/transfers the credit; GamePlayDataManager.StartRun still performs the sole one-shot payment before its start event.

## Merchant flow

ShopDefinitionSO.usesRunGold selects run-shop behavior. ShopDefinition_RunGold.asset uses three unrestricted weapon/relic slots with category weights of 1:3 (25%/75%) and a fourth dedicated Consumable slot, maximum three weapons and one consumable. ShopInventoryRoll retains existing candidate restrictions, including chest-only weapons. Prices are rolled once into saved stock: weapons 1150–1250; Common relics 400–500; Rare 600–700; Epic 900–1000; consumables 850–950, inclusive. The policy centers relic purchasing near a 600-gold unit, potions near 1.5 units (900), and weapons near 2 units (1200).

MerchantNPC stores gold stock under scene/merchant ID/position in existing run merchant states, preserving purchases and prices on revisit. MerchantPurchaseService spends/refunds the selected currency around existing acquisition. MerchantShopPolicy requires an active run for gold shops. Gold shops exclude legacy hub refresh, discount and slot upgrades, but share Sasha's permanent affection stock/pricing benefits with hub shops. Currency selection remains unchanged.

## Permanent merchant affection rewards (2026-11-01)

- The profile's saved affection, plus pending current-run gains, derives cumulative tiers through RunModifierAggregationService. Tier 1 selects one unsold visible item for an integer 10–20% extra discount. The selection/rate is retained in stock DTOs, survives reentry/repricing and remains consumed if that item sells. MerchantRunStateService.RefreshStock resets it for the new stock. Unlocking tier 1 can assign an offer to already stocked unsold goods.
- Tier 2 owns only the capped next-run credit described above. Tier 3 changes eligible Rare/Epic relic candidate weights to 1.10/1.15 versus Common 1.00. ShopInventoryRoll preserves category weights, unlocks, exclusions, uniqueness, consumable-slot rules and zero-bonus RNG behavior. This affects new relic rolls; existing goods do not reroll when the reward unlocks.
- Tier 4 supplies 5% global discount through the existing SashaShopDiscount asset. MerchantOfferPricing calculates original × (1 − global rate) × (1 − special rate), then rounds the final integer once. A 1,200 item with 5% global and 20% special costs 912. Gold base prices preserve their original roll; hub bases come from authored price settings. Both UI and purchase use the resulting stock entry price.
- The hub and run-gold slot prefabs own the folded parchment below the goods. `ShopSlot.RefreshPriceTag` shows the payable stock price beside the shop's currency icon. When the integer price drops, `OriginalPriceText` shows the struck original and `TotalDiscountText` shows the rounded percentage saved against that original. An ordinary discount uses a brown tab and a slot-specific special uses a rose tab. For example, 950 to 722 shows −24%. A full-price item shows its single price, a sold item shows only SOLD on plain paper, and an empty slot hides the entire ticket.
- The three text-free 44×24 paper sprites come from [ShopPriceParchment.png](../../Assets/_Project/Art/Sprites/UI/Common/ShopPriceParchment.png). The prefabs bind the three states and the world-space text. The merchant reward setup menu authors reward data only. See the [B1 implementation record](../SessionLogs/2026-11-04-nadoman354-shop-discount-price-study.md).
- [ShopOriginalPriceText](../../Assets/_Project/Runtime/UI/Shop/ShopOriginalPriceText.cs) centers the strike on the rendered digits when TMP lays out the original price. Both ticket prefabs use the existing `ItemDisplay` sorting layer, with the parchment at order 1 and the three labels and currency icon at order 2. The lightning spear's display group uses order 0 on that layer.
- Initial tuning lives in SashaSpecialOffer, SashaGoldRetention, SashaBetterRelics and SashaShopDiscount under Data/Dialogue/Affection. The setup menus reapply defaults, so balance changes should edit the reward assets directly.

Prefabs/Loot/RunMerchantGroup.prefab is the placement prefab derived from the hub MerchantGroup, with gold shop policy and ShopSlot_RunGold presentation. Its DialogueTrigger now matches the hub Merchant: shared MSShopNpc data, primary Ink, prompt anchor and sprite highlight, offering the same talk prompt, portrait and choices. The four existing authored anchors are all enabled by the shop definition. Existing three-slot saved stock expands through MerchantRunStateService while preserving sold entries. The first three authored anchors use Any and the fourth uses Consumable. Run-gold rolls allow consumables only in the dedicated slot; hub rolls retain their existing policy. Missing saved slots use their actual anchor index when appended. Existing four-slot saved stock is retained until a new run/stock generation. It reuses the hub prefab instantiation path, without creating a new runtime HUD hierarchy.

## Rooms and tuning

Each BossThemes Slime/Dragon/Shadow/DemonKing folder has a themed Shop RoomTemplateSO with the merchant placement. All four corresponding libraries include it. Slime/Dragon/Shadow generation profiles guarantee their shop template. DemonKing uses its own DemonKingShopLayoutPolicy with one shop, referenced by ProceduralDemonkingCorridor; the shared corridor policy is unchanged.

Tune ordinary room budgets in MonsterSpawnRoomGroup, special-event budgets in their event owner, category weights in ShopDefinition_RunGold, price ranges in ShopDefinitionSO.RollGoldPrice, and visual placement in the authored prefabs/room templates. A standard six-Normal/one-Large combat stage pays exactly 900 gold before special-event and boss additions. An Alarm Bell adds at most 50; the boss adds 43–57. This targets about 1.5 baseline relic units per stage and makes a 1200-gold weapon affordable after saving across stages. Actual room composition and purchase cadence still need playtesting.

## Gold Vein kill-reward multiplier (2026-09-18)

- The Common five-level Gold Vein relic applies +10/20/30/40/50% to totals owned by `ExperienceRewardSource` and `BossEncounterEndDirector`, before the existing pickup split.
- Its player-owned runtime carries fractional bonus gold and persists that remainder through the existing relic runtime-state bridge.

## Homing pickups and portal settlement (2026-09-13)

- Magic stones retain their Update-based arrival check within .01 world units and `HomingPickupTravel.Speed = min(40, initialSpeed + 20 * trackingSeconds)`. Their trigger collider has no currency-grant callback. Their serialized speed/delay settings remain unchanged.
- EXP/gold use the combat-gated LateUpdate flow described below, replacing their previous one-second delay and accelerated world-speed motion.
- HomingPickupTravel.TryCollectFollowing performs three active-type queries only on travel, then calls each pickup's guarded collection path for the requested player. It owns no currency, persistent state, scene object or registry. Disabled/consumed pickups and pickups assigned to another player do not grant; failed eligible grants remain and block travel with warning. EXP/gold also settle grounded/rising rewards for the registered player after combat, so an immediate portal cannot discard the batch. Combat still blocks their forced collection and therefore blocks that travel attempt. Stone eligibility remains following-only. Existing consumed flags prevent callback/deferred-Destroy double grants.
- Integration: ScenePortalTravelExecutor before capture/start/end run; SceneConnectionTravelExecutor after departure and before dungeon/player capture/run action; TutorialScenePortal before load plus refreshed player capture; DungeonReturnTravel before warp. Keep this order so level-up-triggered health/cooldown effects enter the outgoing snapshot and magic stones enter the active-run pending ledger before run end.
- New portal implementations should call this helper after access validation and before state capture/run termination/warp. A denied travel request must not grant loot. Successful individual grants remain consumed if another pickup fails or scene loading fails; retries only grant the remainder.
- Gameplay -> Core and Infrastructure -> Gameplay dependency directions retained. No new Manager, singleton or DDOL object. No Architecture/Contracts promotion needed for this small helper.

## Combat reward collection (2026-11-03)

- `MonsterSpawnRoomGroup.IsPlayerInCombat` remains the combat authority: active room waves, live/pending units and encounter holds; outside an entered room it falls back to enemy recognition. `HomingPickupTravel` samples this query once per frame during pickup LateUpdate so both types make the same release decision after combat updates. This one-frame cache resets at SubsystemRegistration and owns no encounter state.
- Each pickup owns one plain `CombatRewardPickupMotion` instance, defined beside the existing travel helper. Grounded pickups remain at their drop position with authored alpha multiplied by 0.45. On clear, they rise 0.25 world units over 0.15 scaled seconds while regaining opacity, then interpolate from the raised origin to the moving player over approximately 0.3 scaled seconds. Shared settings give the same arrival timing regardless of distance, including final-kill drops created before LateUpdate.
- `homingDelay` retains its serialized name and now means the post-combat rise duration. `homingSpeed` retains its name and now means normalized homing progress per second, not world units per second; both prefabs author 3.333333 (about 0.3 seconds). `pickupRenderer`, `groundAlpha`, and `riseHeight` are authored on the two existing pickup prefabs. Existing scene/prefab references and GUIDs remain intact.
- Renewed combat cancels the flight and restores grounded waiting; an interrupted rise returns to its recorded ground position. Disable restores authored alpha and cancels progress, enable/Initialize starts a fresh grounded phase, missing player or paused scaled time prevents progress, and scene unload destroys the owner with no coroutine or event subscription left behind.
- EXP/gold remain the only reward owners and only grant through their existing guarded methods; successful grants keep the existing attached gain particles. EXP's sprite Animator still owns only the color-cycle frames, while this flow owns alpha and position. Magic stones, field heals, reward totals and spawners are unchanged.
- Verification and remaining manual cases: [combat pickup integration record](../../outputs/combat-reward-pickups-2026-11-03/README.md). No new gameplay state save schema, Manager, singleton, or scene object is required.

## Current ownership reconciliation (2026-11-01)

Merchant stock now follows player registration, weapon/relic inventory changes and chest state changes. Existing unsold weapons that match `LootPoolContext.ShopStock` exclusions (including opened-chest leftovers), and relics already at maximum level, are replaced in place through the same stock roller; valid entries, SOLD slots, original run-gold prices and refresh usage are preserved. Retained entries count toward duplicate exclusions and category caps during partial replacement/slot expansion. Inventory callbacks defer reconciliation until the purchase commits its sold state; highlighted slot details follow the resulting entry. [Current merchant rules and ownership](ScriptSystems/ShopStructure.md), [source evidence and validation limits](../SessionLogs/2026-11-01-merchant-owned-weapons/README.md). Final Gameplay MSBuild passed; automatic tests and Unity Play Mode were not executed.

The reciprocal chest rule excludes owned/world/opened-other-chest weapons and unsold merchant weapons. Relic candidates and saved-stock repair now use the same level eligibility as chests. [Follow-up implementation and manual scenarios](../SessionLogs/2026-11-01-chest-shop-policy/README.md).
