# Tutorial Support Structure

## Purpose

The tutorial support layer provides reusable authoring pieces for future tutorials without defining tutorial steps or scene content.

## Current Structure

- `TutorialInfoPanel` is the scene/prefab-authored UI driver for a tutorial explanation panel, including optional shared hold-button progress projection.
- `TutorialInfoTrigger` opens a panel from a 2D trigger or from public methods such as `Fire`, `FireNow`, and `FireAfterDelay`. A `Collider2D` is needed only for trigger-entry activation, not for direct UnityEvent/code calls.
- `TutorialProgressStore` reads and writes tutorial completion through `GameDataManager`.
- `HubIntroProgressGate` centralizes the post-DarkLord Hub intro ids: `darklord_tutorial_forced_defeat_completed` and `hub_intro_after_darklord_seen`. It also owns the editor-only bypass check used by both the Hub fall presentation and the Hub intro sequence.
- `TutorialSaveData` stores completed tutorial ids in `GameData.tutorialData.completedTutorialIds`.
- `Assets/Sprites/UI/Tutorial/TutorialInfoWindow.png` and `TutorialInfoTitleRibbon.png` are the imported tutorial panel/title sprite assets.
- `TutorialInfoPage` is the authored page data shape for repeated tutorial layouts: page title, body text, and content image.
- `TutorialSceneSequenceDirector` is a scene-authored event coordinator for tutorial scene beats such as scene start, trigger entry, combat start, monster clear, chest open, portal entry, door open/close, player control lock, and player targetability blocking.
- `TutorialPlayerAutoMove` moves the authored player transform to a target point for tutorial presentation. It prefers existing `ExternalMovementController2D` / `MovementMotor2D` cleanup when present and falls back to Rigidbody2D or Transform movement.
- `TutorialBossEncounterSequence` coordinates the tutorial-only boss encounter flow: wait for and track player registration, hide normal runtime HUD roots, apply an authored initial player aim direction before locking player presentation, hold transition/player control/targetability locks, wait for scene transition fade to finish, briefly frame the player, boss camera focus, optional boss sprite scale, first dialogue, letterboxed scripted lasers, presentation HP HUD visibility, player hit feedback, immediate presentation death when tutorial HP reaches zero, second dialogue, player camera return without a second letterbox, and fake game-over presentation.
- `HubIntroAfterDarkLordSequence` is a Hub scene-authored continuation after the DarkLord forced-loss flow. It gates on the shared completion/seen ids, hides `GameplayHUDCanvas`, waits for the Hub fall presentation, locks player control, shows letterbox bars only for the opening NPC SpeechBubble beat, pre-sizes that opening SpeechBubble before typing, removes the bars before Dialogue, focuses the existing gameplay camera on the NPC and three authored Hub points, plays Dialogue segments, restores all temporary state, and marks the Hub intro seen.
- `TutorialBossLaserPresentation` plays authored Demon King laser steps without connecting to real boss AI or damage. Each step can reduce only the presentation HP view.
- `TutorialPresentationHpView` projects tutorial-only HP through authored text, simple active roots, or `HeartTokenUI` slots. It does not read or write player `AttributeSet` or death state.
- `DarkLordTutorialAuthoringTool` is an Editor-only scene authoring menu for `DarkLord_Tutorial`. It creates the tutorial boss presentation root, focus targets, an `InitialAimTarget` marker, laser origins, a 3-slot presentation HP view using the existing `GlobalUIRoot` heart HUD layout/style, sequence/laser components, dialogue references when compiled Ink JSON exists, removes tutorial-unneeded real-boss runtime components from the scene `DemonKing` instance, and validates that conflicting real boss paths are absent.
- `HubIntroAfterDarkLordAuthoringTool` is an Editor-only scene authoring menu for `ProtoTypeHub`. It creates the Hub intro root and NPC/junk/training dummy/gate focus targets, adds/configures `HubIntroAfterDarkLordSequence`, configures the `PlayerSpawner.playerPrefab` `PlayerHubSpawnPresentation2D` gate/auto-wake defaults, can wire `MSUpgradeNpc` plus temporary Hub intro Ink JSON assets and their knot start paths for flow testing, and validates the remaining NPCData/Ink/scene reference wiring.
- `TutorialDefaultWeaponBootstrap` is a scene-authored tutorial loadout correction script. It forces the current player `WeaponInventory2D` to hold and equip the configured default weapon, optionally clearing other weapon slots.
- `TutorialScenePortal` is a tutorial-only direct scene portal for fixed authored jumps such as `TutorialCorridor` to `DarkLord_Tutorial`. It uses `SceneTransitionCoordinator`, prepares a minimal pending transition context, captures the current player runtime state before load, and does not create or consume a `PortalRouteManager` run plan.
- `TutorialDoorClosedTrigger` is a tutorial bridge that listens to `DoorObject.ClosedPresentationCompleted` and invokes an authored UnityEvent after a target door's close presentation completes. It can optionally require an assigned `RoomDoorMonsterKillLock` to be in an active encounter with remaining monsters.
- `TutorialCombatIntroSequence` is a scene-authored combat tutorial intro coordinator for the door-closed beat. It locks player controls, blocks player targetability, plays the cinematic letterbox, focuses the gameplay camera on an authored monster/chest target, fires the attack/skill `TutorialInfoTrigger`, waits for the panel to close, returns the camera to the player, plays letterbox-out, then releases gameplay.
- `TutorialChestOpenedTrigger` is a tutorial bridge that listens to a target `TreasureChest` successful UI-open event and invokes an authored UnityEvent for the next tutorial step.
- `TutorialPlayerHealthAutoRecover` is a scene-authored tutorial safety component that restores the current player HP attribute to max immediately after HP or max HP changes. It can temporarily disable `PlayerDeathReturnToHub2D` while active so a tutorial scene cannot route to game over before the recovery lands.

## Ownership And Lifecycle

- UI hierarchy, canvas, TMP text, Images, and sprite assignment should be authored in a scene or prefab, then referenced by `TutorialInfoPanel`.
- `TutorialInfoPanel.hideOnPlayStart` defaults to enabled so an authored active UI can be reviewed in Scene view but is hidden automatically when Play Mode starts.
- `TutorialInfoPanel` blocks normal gameplay input while open through `GameFlowInputBlocker` when `blockGameFlowWhileOpen` is enabled.
- `TutorialInfoPanel` owns page index state. Prev/Next controls are scene-authored buttons whose roots stay visible while multiple pages exist; invalid directions are disabled through `Button.interactable` instead of hidden. Optional `pageNumberText` displays the current page as `1/2`. A/D page keys use `InputKeyCompatibility` and do not require runtime-created UI. Optional page key guide roots and KeyGlyph Images stay visible while multiple pages exist, with invalid directions projected through disabled color/tint.
- The hold-confirm button is only active/usable on the final page. Before the final page, `TutorialInfoPanel` resets hold progress, disables the authored `HoldActionButton`, and deactivates the authored hold-button root.
- Panel progress uses an authored `HoldActionButton` when assigned. In that mode the button's own hold time, input settings, and reset policy are the source of truth.
- If no `HoldActionButton` is assigned, `TutorialInfoPanel` falls back to the existing `InputBindingService` `DialogueAdvance` binding and uses request/panel hold seconds.
- `TutorialInfoTrigger` can be placed on a trigger collider for player entry, or fired directly from code/UnityEvent for specific timing. Direct-call triggers do not need a `Collider2D`.
- `TutorialSceneSequenceDirector` can optionally wait for an active `SceneTransitionCoordinator` / `SceneFadeTransitionService` transition to finish before firing scene-start events. By default it starts its scene-start delay as soon as the tutorial scene is loaded, which is the intended path for post-title FadeOut startup beats.
- Completion persistence is opt-in per request/trigger and should use stable non-empty tutorial ids.
- Open presentation is owned by the panel: an optional authored `dimPanel` `CanvasGroup` fades in while an optional authored `tutorialPanel` root moves up from `hiddenPanelOffset` using an overshoot ease. Close plays the reverse and deactivates the root after the presentation finishes.
- Tutorial scene flow scripts do not create scene content. Doors, HP UI, laser origins, boss visuals, camera focus targets, collapse effects, and scene portals remain authored in Unity and are connected through serialized references or UnityEvents.
- `TutorialBossEncounterSequence` may use `CameraPresentationDirector` when a boss-camera setup exists, but its default tutorial path focuses the existing gameplay camera through `CameraBootstrap` so a non-boss tutorial scene can still frame a placed boss sprite. Tutorial camera focus/return waits treat serialized wait seconds as minimum holds, then wait for the camera to settle on the target.
- `TutorialBossEncounterSequence` waits for `PlayerRuntimeRegistry`/`PlayerInteractor2D`, subscribes to player register/unregister events, and holds a `SceneFadeTransitionService` player-unlock blocker before acquiring player protection. Serialized validation can confirm the lock fields, but only runtime player resolution proves the lock was actually acquired.
- `TutorialBossEncounterSequence.applyInitialAimOnSequenceStart` is applied immediately before `PlayerCinematicProtection` disables `PlayerAim2D` and before `WeaponPresentationRig2D` acquires its cinematic presentation lock. When `initialAimTarget` is assigned, the sequence aims from the spawned player toward that marker; otherwise it uses `fallbackInitialAimDirection`.
- `TutorialBossEncounterSequence.keepPlayerLockedAfterSequence` is enabled for `DarkLord_Tutorial` because the scene has no intended player-control window. Completion cleanup releases camera, letterbox, UI input blocker, and timer pause, but keeps player protection/targetability and the transition unlock blocker until the component disables or the scene unloads.
- `TutorialBossEncounterSequence` keeps letterbox bars off while Ink dialogue is visible. It turns the bars on only for non-dialogue presentation beats, so Dialogue UI, speaker name, and choices are not covered.
- In `DarkLord_Tutorial`, the authoring tool disables the `CameraPresentationDirector` path and uses `BossFocusTarget` / `PlayerFocusTarget` through the gameplay camera. This keeps the tutorial sequence independent from real boss `BossCam` authoring.
- Fake tutorial game-over calls `GameOverPresentationController.TryShow(...)` with `GameOverPresentationRequest.EndRunOnReturn = false`, tutorial-only `ReturnButtonLabel = "추락"`, message override `처치자 마왕`, location override `마왕의 알현실`, and hidden remaining-time text; real HP, real death components, normal game-over text, and run end state are not changed by the tutorial sequence.
- Before fake tutorial game-over opens, `TutorialBossEncounterSequence` marks `darklord_tutorial_forced_defeat_completed` so Hub-side introduction gates can distinguish this route from ordinary first Hub entry.
- `PlayerHubSpawnPresentation2D` can keep its default `AnyHubSpawn` behavior, or be set to `AfterDarkLordTutorialUntilSeen` for the post-DarkLord Hub route. In that mode it uses `HubIntroProgressGate` and can wake the player automatically through `autoWakeWithoutInput` / `autoWakeDelaySeconds`.
- `HubIntroAfterDarkLordSequence` hides only the existing `GameplayHUDCanvas` and restores its previous enabled state on completion/cancel. It does not author or instantiate gameplay HUD UI.
- The Hub intro sequence waits until `PlayerHubSpawnPresentation2D.IsPlaying` is false before acquiring `PlayerCinematicProtection`, because the fall presentation restores player input on wake.
- The Hub intro opening SpeechBubble uses the existing pre-sized speech-bubble path from RunSpecial NPC when `preSizeOpeningSpeechBubbleBeforeTyping` is enabled. This measures the full line, clamps text width, and grows the bubble before the typing tween starts.
- The Hub intro sequence removes cinematic letterbox bars after the opening NPC SpeechBubble and before starting any Ink Dialogue, so the Dialogue UI is not covered during the three Hub focus explanations or final NPC segment.
- Dialogue presentation options extend the existing Dialogue path without changing default callers. Hub focus steps use no portrait intro/outro; the final NPC segment can use a fast silhouette portrait intro.
- Dialogue opening previews the first playable Ink line without consuming it and passes that line's `face` tag to the portrait intro. Boss silhouette intros therefore use the first authored expression, such as `# face:Tutorial`, instead of always starting from `Normal`.
- `DarkLordTutorialAuthoringTool` creates a `TutorialPresentationHpCanvas` as a temporary presentation-only HP readout with three heart slots copied from the existing HUD token/sprite style and layout. It deactivates the normal Gameplay/Boss HUD roots for `DarkLord_Tutorial`; the tutorial HP canvas is hidden during Script 1, shown for the laser letterbox sequence, hidden before Script 2, and is not connected to actual player `AttributeSet` HP or death behavior.
- When `DarkLord_Tutorial` unloads or the sequence is canceled with lock release, `TutorialBossEncounterSequence` restores a snapshot of the normal Gameplay/Boss HUD canvas roots and default HUD component root active states so the persisted `GlobalUIRoot` can show normal HUD again in Hub without forcing previously hidden elements on.
- Tutorial boss player locks use `PlayerCinematicProtection`, which now combines input behaviour disabling with the existing UI control block tag set and an explicit `State.Move.Dash.Blocked` tag. This is required because cached movement sources and GAS dash activation can outlive a simple input component disable.
- Tutorial-only default weapon enforcement is scene-local. `TutorialDefaultWeaponBootstrap` uses `WeaponInventory2D.TrySetWeaponSlot(...)` and `Equip(...)` so existing weapon removal, stat binding, presentation binding, ability ownership, and equipped-change events remain owned by the weapon inventory path.
- `TutorialDefaultWeaponBootstrap.applyOnStart` waits authored startup frames before applying so player spawn and pending runtime restore have a chance to finish first. Use `ApplyNow()` from a scene director/UnityEvent when the tutorial needs an explicit timing point.
- A tutorial-only weapon that must survive scene travel still has to be registered in the active `ItemDatabase.allWeapons`, because player runtime restore resolves captured weapon ids through `ItemManager`. It does not need to be in `defaultUnlockedWeapons` unless normal unlock/drop access is intended.
- Tutorial fixed scene travel should not use `ScenePortal` unless the travel is intentionally part of the normal run route plan. `TutorialScenePortal` owns direct scene load interaction, visual highlight projection, current player runtime-state capture, and a minimal pending transition context for the destination `PlayerSpawner`/restore bootstrapper.
- Combat tutorial prompts that must wait until the room door visually closes should use `TutorialDoorClosedTrigger` instead of guessing with a trigger delay. `DoorObject` owns only the generic close-completion signal; tutorial panel or sequence calls remain wired through the bridge UnityEvent.
- Combat tutorial intro presentation should use `TutorialCombatIntroSequence` when the authored flow needs camera focus before the attack/skill prompt. The sequence owns only temporary control/targetability/camera/letterbox ownership and releases gameplay after camera return and letterbox-out finish before raising its gameplay-released event.
- Combat tutorial chest continuation should use `TutorialSceneSequenceDirector.OnMonstersCleared` for the post-combat chest-open prompt, then `TutorialChestOpenedTrigger.OnChestOpened` for the step that should run after the chest UI opens.
- Tutorial scene HP auto-recovery should stay scene-local through `TutorialPlayerHealthAutoRecover`; do not change shared player damage, death, or combat rules for this tutorial exception.

## Extension Entry Points

- Add authored panel prefab/scene wiring by assigning `TutorialInfoPanel` references.
- Leave `hideOnPlayStart` enabled for scene-authored tutorial UI so test runs start with the panel hidden. Disable it only for a focused UI preview scene that intentionally starts with the panel visible.
- Add tutorial content by filling `TutorialInfoTrigger.pages`. Page data is the only tutorial content path; empty pages open a blank panel and should be treated as an authoring miss.
- Assign `previousPageButton` / `nextPageButton` and, when the clickable visual root differs from the Button GameObject, assign `previousPageRoot` / `nextPageRoot` so the controls can stay visible while their `Button.interactable` state changes. Assign `pageNumberText` when the authored layout should show `current/total`.
- Assign `pageKeyGuideRoot`, `previousPageKeyGuideRoot`, `nextPageKeyGuideRoot`, and optional `previousPageKeyGlyphImage` / `nextPageKeyGlyphImage` when the authored layout should show A/D page navigation hints. If the Image references are left empty, `TutorialInfoPanel` resolves an `Image` under each guide root. The individual A/D guide roots stay visible while multiple pages exist, and invalid directions use `disabledPageKeyGlyphColor`.
- Assign `dimPanel` and `tutorialPanel` when open/close presentation is desired. Leave them empty for immediate legacy-style show/hide.
- Add a hold-confirm button by authoring a `HoldFillButtonView` and optional `HoldActionButton`, then assigning them to `TutorialInfoPanel`. Assign `advanceHoldButtonRoot` when the visual root differs from the `HoldActionButton` GameObject.
- Set per-layout hold timing on the authored `HoldActionButton` prefab/variant when a button is assigned; `TutorialInfoTrigger.holdSeconds` remains fallback-only for buttonless panels.
- Add tutorial timing by calling `TutorialInfoTrigger.FireNow` or `FireAfterDelay`.
- For event-driven tutorial timing such as door-close prompts, place `TutorialInfoTrigger` on any convenient scene object without a collider and call `FireNow()` from the owning sequence or UnityEvent.
- Add one-shot guidance by setting `usePersistentCompletion` and `markCompletedOnClose` with a stable `tutorialId`.
- Add scene flow by placing `TutorialSceneSequenceDirector` in the tutorial scene and wiring its UnityEvents from trigger colliders, chest open events, monster clear locks, portal entry, and authored door controls. For intro-to-tutorial startup, enable `playOnStart`, leave `waitForSceneTransitionBeforeStart` disabled, set `startDelaySeconds`, then wire `onSceneStarted` to the first `TutorialPlayerAutoMove.MoveToTarget`. Enable `waitForSceneTransitionBeforeStart` only when the scene-start event should wait until fade-in and the full transition session are complete.
- Add a start walk-in by wiring `TutorialPlayerAutoMove.MoveToTarget` from the scene director or a trigger event. Assign the player, target point, and existing movement components when available.
- Add tutorial boss encounter by placing `TutorialBossEncounterSequence`, assigning a tutorial-only `NPCData`, first/second Ink TextAssets, optional `TutorialBossLaserPresentation`, optional `TutorialPresentationHpView`, boss focus target, boss visual root, and fake game-over return scene.
- Add the post-DarkLord Hub introduction by setting the Hub player prefab/instance `PlayerHubSpawnPresentation2D.playCondition` to `AfterDarkLordTutorialUntilSeen`, enabling `autoWakeWithoutInput` if the player should rise without input, and placing `HubIntroAfterDarkLordSequence` in the Hub scene.
- For `HubIntroAfterDarkLordSequence`, assign the NPC SpeechBubble, NPC focus target, narrator `NPCData`, three focus steps for junk/training dummy/gate, the final NPC focus/dialogue, and matching completion/seen ids. Leave runtime UI hierarchy creation out of the scene; use existing Dialogue, SpeechBubble, and letterbox patterns.
- Use the opening SpeechBubble layout fields when the intro bark is long: leave `preSizeOpeningSpeechBubbleBeforeTyping` enabled, keep min/max text width near the RunSpecial defaults of `160`/`360`, and tune only if the authored bubble art or camera framing requires a different width.
- For `ProtoTypeHub`, prefer running `Tools/Tutorial/Hub Intro After DarkLord/Apply Default Authoring To Active Scene`, then run `Tools/Tutorial/Hub Intro After DarkLord/Create Or Wire Draft Dialogue Assets` if final NPCData/Ink content is not ready, then run `Validate Active Scene`. The tool selects the generated root and marks the scene/player prefab dirty when it changes them; save only after reviewing focus target positions and assigned references.
- For `DarkLord_Tutorial`, prefer running `Tools/Tutorial/DarkLord Tutorial/Apply Default Authoring To Active Scene` with that scene active, then run `Validate Active Scene` after Unity finishes importing/compiling the tutorial Ink files. Save the scene only after reviewing the generated root, references, and `InitialAimTarget` position.
- Add laser beats by filling `TutorialBossLaserPresentation.steps` with origin transforms, direction, length, width, warning/attack timing, optional opposite ray, and an authored `DemonKingEgoLaserVfx` prefab.
- Use `TutorialBossEncounterSequence` UnityEvents for authored hit, collapse, sound, VFX, and animation hooks instead of connecting to real death/damage systems.
- Add tutorial-only default loadout by placing `TutorialDefaultWeaponBootstrap`, assigning the intended `defaultWeapon`, and leaving `clearOtherWeaponSlots` enabled when the scene must start with only that weapon.
- Add a tutorial-only fixed portal by placing an interactable object with a trigger `Collider2D`, adding `TutorialScenePortal`, and setting `targetSceneName` to the destination scene, for example `DarkLord_Tutorial`. Leave `resetPlayerRuntimeStateOnTravel` disabled when the destination should keep the tutorial loadout. The destination scene must be in BuildSettings.
- Add a simple combat-room close prompt by placing `TutorialDoorClosedTrigger` on or near the target door, assigning the `DoorObject`, optionally assigning the room's `RoomDoorMonsterKillLock`, and wiring `OnDoorClosed` to `TutorialInfoTrigger.FireNow()` or a `TutorialSceneSequenceDirector` method.
- Add the attack/skill combat intro by placing `TutorialCombatIntroSequence`, assigning the same `TutorialDoorClosedTrigger` or wiring the trigger's `OnDoorClosed` to `BeginSequence`, assigning `focusTarget` to an authored marker near the monster/chest composition, assigning the attack/skill `TutorialInfoTrigger`, and assigning the shared `TutorialInfoPanel` when the sequence should wait until the panel closes. Leave `useLetterbox` enabled for the cinematic bars. Leave `fadeGlobalUiDuringLetterbox` disabled unless the target tutorial panel is on a layer that will stay visible.
- Use `TutorialCombatIntroSequence.OnGameplayReleased` for authored events that should happen only after the camera returns to the player, letterbox-out completes, and control/targetability are restored.
- Add post-combat chest guidance by assigning `TutorialSceneSequenceDirector.chestMonsterKillLock` or `roomDoorMonsterKillLock`, starting its monster-clear wait from the combat-start/release beat, and wiring `OnMonstersCleared` to the chest-open `TutorialInfoTrigger.FireNow()`.
- Add chest-open continuation by placing `TutorialChestOpenedTrigger` on the target chest or a nearby scene object, assigning the target `TreasureChest`, and wiring `OnChestOpened` to `TutorialSceneSequenceDirector.NotifyChestOpened()` plus any next `TutorialInfoTrigger.FireNow()` call.
- Add tutorial HP safety by placing `TutorialPlayerHealthAutoRecover` in the tutorial scene and assigning the player `AttributeSet`, health `AttributeDefinition`, and max-health `AttributeDefinition`. Leave `suspendPlayerDeathReturn` enabled when the scene must never route to game over from combat damage.

## Known Pitfalls

- Empty tutorial ids are never recorded as completed.
- The Hub fall presentation and Hub intro sequence must use the same completion/seen ids. If one object uses editor bypass and the other does not, direct Hub Play Mode testing can skip either the fall or the follow-up intro.
- Missing Hub intro Dialogue TextAssets or narrator `NPCData` are authoring mistakes. The sequence logs missing narrator/service errors, but scene wiring and Play Mode review are still required to confirm every dialogue segment appears.
- `HubIntroAfterDarkLordAuthoringTool` can add/configure `PlayerHubSpawnPresentation2D` on `PlayerSpawner.playerPrefab`; this is a prefab-facing editor action, not a runtime mutation. Review the prefab dirty state before saving, especially if another scene also uses the same player prefab.
- `HubIntroAfterDarkLordAuthoringTool` wires the existing `MSUpgradeNpc.asset` as the temporary narrator and uses temporary Ink/JSON TextAssets under `Assets/LeeJunMo/Datas/Inks/HubIntroAfterDarkLord` to unblock flow validation. These assets are knot-based, so the tool also fills and validates the matching `dialogueStartPath` / `finalDialogueStartPath` values. These are placeholders for play-flow testing; replace their text before final content sign-off.
- `HubIntroAfterDarkLordAuthoringTool` does not create SpeechBubble prefabs or runtime UI hierarchy. Validation errors for missing `narratorNpcData`, `openingSpeechText`, focus step Ink JSON, and final Ink JSON can be resolved either by final Inspector wiring or by the draft dialogue asset menu.
- If the Hub intro opening SpeechBubble extends off-screen while typing, confirm `preSizeOpeningSpeechBubbleBeforeTyping` is enabled and `openingSpeechBubbleMaxTextWidth` is not set too high. The Dialogue segments are unrelated because they use the Dialogue UI, not the SpeechBubble layout path.
- The Hub intro sequence adds `PlayerCinematicProtection` at runtime only as the existing protection pattern when the player lacks it; it does not add a new manager or persistent object.
- Unity import/compile must refresh new script and sprite metadata before prefab wiring.
- `TutorialInfoTrigger` no longer requires a `Collider2D`. If a tutorial should fire from player entry, the scene object must still have an authored trigger `Collider2D`; otherwise only `Fire`, `FireNow`, or `FireAfterDelay` calls will open it.
- Do not expect `TutorialInfoTrigger.holdSeconds` to override an assigned `HoldActionButton`; change the button prefab/variant when a button-led tutorial needs a different hold duration.
- Page title text comes from `TutorialInfoPage.title`. Leave a page title empty only when the authored panel title should be blank for that page.
- Page key guide sprites are visual-only. Changing a KeyGlyph Image sprite manually can be overwritten from `InputGlyphDatabase`; change `previousPageKey` / `nextPageKey` for actual keyboard navigation.
- Prev/Next disabled visuals now depend on the authored `Button` transition/color settings. Key guide disabled visuals use `disabledPageKeyGlyphColor` and restore each Image's authored color when the direction becomes valid again.
- `tutorialPanel` should point to the actual TutorialPanel/content root, not the full-screen root that contains `DimPanel`; otherwise the whole overlay can move.
- `dimPanel` should point to the DimPanel child/sibling `CanvasGroup`, not the same root that owns `TutorialInfoPanel`. The runtime avoids deactivating the panel root if misassigned, but the fade authoring is clearer with a dedicated DimPanel object.
- Presentation HP must stay separate from actual player HP. Do not call player damage, death, or `AttributeSet` mutation from tutorial boss laser UnityEvents unless the tutorial design explicitly changes to real damage.
- Tutorial boss laser hits may call `PlayerHitFeedback2D`, and collapse may call `PlayerDeathPresentation2D`, but these are presentation-only calls. Do not use `PlayerDeathReturnToHub2D` or real HP mutation for the scripted failure unless the design explicitly changes.
- A passing `DarkLordTutorialAuthoringTool` validation does not prove the runtime player lock was acquired. Play Mode review must confirm `TutorialBossEncounterSequence` waited for player registration and that movement/dash/combat/aim input stays blocked.
- If the copied `DemonKing` scene instance keeps `BossDialogueRunner`, `BossEncounterDirector`, or combat/FSM components, the normal boss dialogue or combat path can race the tutorial sequence. Rerun the DarkLord authoring Apply menu and validate that tutorial-unneeded runtime components were removed from the scene instance.
- If `DarkLord_Tutorial` authoring was applied before the HUD-layout HP and permanent-lock defaults, rerun the Apply menu and save the scene after review.
- If tutorial HP should remain visible during letterbox, put it on a canvas/layer that is not included in `TutorialBossEncounterSequence.fadedLayers`, or disable `useCustomFadedLayers` only when default global UI fading is acceptable.
- If the boss focus camera does not move in `DarkLord_Tutorial`, rerun the DarkLord authoring Apply menu and validate that `useCameraPresentationDirector` is disabled. The tutorial should not depend on the real boss `BossCam` path.
- If entering `DarkLord_Tutorial` from `TutorialScene` shows normal HUD during fade-in, confirm `TutorialBossEncounterSequence.hideDefaultHudDuringSequence` is enabled and the sequence starts on scene load. Scene-only inactive HUD authoring does not affect an already-persisted `GlobalUIRoot`.
- If the player or equipped weapon faces the wrong way at `DarkLord_Tutorial` entry, move `__TutorialBossPresentation/InitialAimTarget` in Scene View and rerun validation. The marker controls the initial `PlayerAim2D` direction captured by the cinematic weapon presentation lock.
- If the fake HP UI is referenced but invisible, inspect `TutorialPresentationHpCanvas` first. Its GameObject must be active, its RectTransform should match the full-screen overlay authoring defaults, and its canvas sorting must be high enough to render above the cinematic letterbox. Visibility should be controlled by `TutorialPresentationHpView.visibilityGroup` alpha, not by disabling or stale canvas authoring.
- Tutorial boss Ink line text should not include visible speaker prefixes such as `마왕:`. Use `# speaker: 1005` for DarkLord lines and `# speaker: ???` for temporary hidden-speaker lines.
- Tutorial boss Ink that needs a non-`Normal` opening silhouette should put the intended expression on the first playable line with `# face:Tutorial` or `# face:1005:Tutorial`. The Dialogue preview does not advance the real Ink story, but Play Mode should confirm the sprite label exists in the assigned `SpriteLibraryAsset`.
- For TMP rich text inside Ink body text, avoid raw hex color tags such as `<color=#A855F7>` unless the generated JSON is verified. Ink can parse `#A855F7...` as an Ink tag and leave only `<color=` in the visible line. Prefer named colors such as `<color=purple>` for tutorial dialogue.
- The auto-created tutorial boss HP canvas is a temporary authoring convenience. Replace it with an authored scene/prefab UI later if the final tutorial HUD needs custom art or layout.
- New tutorial boss scripts add MonoBehaviours and serialized references, so Unity Editor import/compile and Inspector wiring are required before scene authoring can be considered complete.
- `DarkLordTutorialAuthoringTool` does not edit scene YAML directly and does not save the scene. The active scene must be `DarkLord_Tutorial`, Play Mode must be stopped, and the user must save after reviewing the dirty scene.
- The DarkLord tutorial Ink `.json` references are generated by Unity import. Until `TutorialDarkLordScript1.json` and `TutorialDarkLordScript2.json` exist, Apply/Validate will report missing dialogue TextAssets even though the `.ink` sources are present.
- Automated laser origins, HP canvas placement, and camera focus targets are defaults only. Scene View tuning is still required if the copied boss room layout or player spawn differs from the assumed positions.
- The system currently provides only the common frame and boss encounter support scripts; actual tutorial text, enemy/chest/gate placement, Ink content, and layout positions remain out of scope.
- `TutorialDefaultWeaponBootstrap` changes the live player inventory for the current runtime session. If a later transition should discard tutorial loadout state, that transition should reset or replace the run state deliberately instead of relying on this script to preserve the previous loadout.
- If a tutorial default weapon is captured but disappears after scene travel, confirm the weapon asset is present in `ItemDatabase.allWeapons`. `PlayerRuntimeResolverBridge.ResolveWeapon(...)` cannot restore a captured `weaponId` that the active item database cannot resolve.
- `TutorialScenePortal` bypasses the normal portal route pipeline but still captures current player runtime state directly. If a future tutorial portal intentionally must discard the current loadout, enable `resetPlayerRuntimeStateOnTravel` or reset the destination loadout deliberately.
- `TutorialDoorClosedTrigger` depends on `DoorObject` close-completion detection. Animator-driven doors complete when the animator reaches the closed `Idle` state, a non-looping close state finishes, or the fallback timeout is reached; an optional `OnCloseAnimationComplete` animation event can make authored timing explicit.
- `TutorialCombatIntroSequence` swaps the existing gameplay camera's Follow/LookAt targets. Manual validation should confirm the authored focus marker frames both monster and chest at the selected orthographic size, and that camera return damping feels acceptable.
- `TutorialCombatIntroSequence.fadeGlobalUiDuringLetterbox` is disabled by default so the attack/skill tutorial panel is not faded out by the cinematic overlay. If enabled, review `fadedLayers` carefully because the default `CinematicLetterboxOverlay` layer set includes prompt/dialogue-style UI.
- `TutorialCombatIntroSequence` releases targetability only after returning to the player. If another scene event also acquires `PlayerTargetabilityBlocker`, enemies may still ignore the player until that owner releases its token.
- `TutorialChestOpenedTrigger` fires from `TreasureChest.FirstOpenedUi` by default, which is raised after `ChestUIManager.OpenChest(...)` succeeds. It will not fire if the chest interaction request starts but the chest UI fails to open.
- If a tutorial should respond every time an already-open chest UI is reopened, disable `firstOpenOnly`; otherwise leave `triggerOnce` and `firstOpenOnly` enabled for one-shot tutorial continuation.
- `TutorialPlayerHealthAutoRecover` changes live player HP state and can temporarily disable `PlayerDeathReturnToHub2D`. Keep it out of non-tutorial scenes and verify the health/max-health attribute references in the Inspector.
