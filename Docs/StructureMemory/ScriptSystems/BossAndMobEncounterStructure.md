# Boss And Mob Encounter Structure

## Purpose

Map boss, mob, spawn, hazard, lock, and shared enemy combat scripts before any physical reorganization.

The file name is kept for link stability, but the working boundary is no longer "everything is an encounter".
Bosses use an `Encounter -> Battle -> BattleEnd` flow. General mobs use `Population / Spawn -> Battle Runtime -> Death Result`, with optional room/chest lock overlays.

## Flow Boundary Map

| Flow boundary | Primary scripts | Responsibility |
| --- | --- | --- |
| Boss Encounter | Boss encounter intro, dialogue, target activation, combat entry hooks. | Prepare the boss fight and start combat. It should not own rewards, portals, or persistent run result processing. |
| Boss Battle | Boss FSM core/states/configs, boss-specific controllers, boss abilities, pattern actors, BT/GAS bridge. | Run the fight: phase evaluation, pattern selection/execution, damage/status interaction, groggy, and attack presentation. |
| Boss BattleEnd | Boss death presentation, optional `BossDefeatEndingSequence`, `RunProgressCoordinator`, active route context, route-linked `BossSpecialRewardPresetSO`, scene-authored `BossBattleEndHandler`, authored `TreasureChest`/`ScenePortal` references, TreasureChest reward dust reveal, optional portal `BossRewardObjectRevealPresentation`, physical magic stone/field-heal drops, and `BossRewardFallbackService`. | Convert boss defeat into run/world results. The former `BossDrop` adapter and split reward/portal/anchor components have been removed; normal-route contexts are the default chest-plus-portal reward path, final-route contexts skip chest activation by default, and an explicitly authored terminal ending sequence can replace rewards/portal entirely for a selected boss. |
| Mob Population / Spawn | `MonsterSpawner`, `SceneMonsterSpawnDirector`, spawn containers, room groups/profiles, difficulty/context/pathfinding injection. | Instantiate and configure general mobs. This is the normal placement entry point for mobs, not a boss-style encounter. |
| Mob Battle Runtime | `Mob`, mob FSM, chase/facing/home return, attack decision source, `MobAbilityCoordinator`, pattern runners, mob ability logic. | Keep spawned mobs battle-ready, run chase/attack behavior, and perform cleanup according to `Docs/Contracts/MobCleanupContract.md`. |
| Mob Death Result | `Mob.OnDeathStarted`, monster loot spawn, runtime no-loot marker, spawned-monster tracking cleanup. | Convert mob death into immediate results. Spawn-registered mobs drop normally; runtime split and boss/local summoned mobs can suppress the monster loot request. Long-term clear/lock semantics should not be assumed from root GameObject destruction alone. |
| Room / Chest Lock Overlay | `RoomDoorMonsterKillLock`, `ChestMonsterKillLock`, `ChestMonsterKillLockNavigationView`, `RoomEnemyNavigationOverlay`, spawn-time lock registration. | Observe registered combatants, unlock doors/chests, and show local chest/room guidance presentation. Count spawn-registered tracking units; Slime split descendants join the parent's unit and do not create additional lock counts. Room enemy guidance is camera-edge placement from the active `MonsterSpawnRoomGroup`, not a scene-wide enemy scan. |
| Hazards / Puddles | Puddle runtime, conversion service, hazard damage, puddle visuals, boss-specific puddle interaction triggers. | Battle environment. Boss-specific triggers can live in boss ability logic, but hazard actors should avoid accumulating boss-specific policy. |
| Enemy Shared Combat | `Enemy`, death command, shared cleanup utility. | Shared enemy combat base, cleanup helpers, and canonical player target resolution for player-owned child/orbit colliders. |

### Demon King Boss Pattern Polish Notes

- `DarkLordBoss.controller` is a transition-free state library. DemonKing body animation is played by named states from `DemonKingController`; pattern timing, damage, and VFX remain in `DemonKingAbilityLogics.cs`, not in animation events.
- DemonKing non-laser VFX still load through `Resources/DemonKing/Vfx` prefabs generated by `DemonKingPatternVfxAssetBuilder`. New DarkLord effect sheets should be added to that builder instead of loading PNG frames directly from runtime code.
- DemonKing precise VFX output points can be tuned through `DemonKingVfxSocketMap`. Sockets are authored in the DarkLord sprite's natural left-facing baseline and mirror X when the boss faces right. Optional child anchors override numeric offsets; if the map or a socket is missing, runtime falls back to the existing pattern positions. Current sockets cover eye flash, hand cast/counter impact, sword slash/stab origins, foot landing impact, HP50 charge loop/disappear, and HomingMagic stock center. Selected-object gizmos show socket positions, while `EgoSwordActor` selected gizmos show held/throw/recall offsets, laser VFX origin offset, and vertical/plant impact diameter.
- `DarkLordExplosion2` is an opt-in delayed explosion style for HeavySlash follow-up line explosions, Bombardment lane explosions, and 10% FinalDesperation bombs only. Other delayed/radial/final-jump explosion paths keep the existing `DemonKingExplosionVfx` unless explicitly changed.
- Circular explosion/impact cue overrides are directionless: runtime uses the cue's rotation offset only and does not add the supplied direction angle. Directional VFX such as Slash, Stab, Charge, Laser, and projectiles still rotate from their attack direction.
- `DemonKingImpactVfx` can leave a separate `DarkLordFragment` crack for a timed hold/fade. EgoSword fixed-ground states own their own persistent fragment and clear it on throw, recall, hide, disable, or battle cleanup so the crack does not duplicate the timed impact fragment.
- `DemonKingExplosionVfx`, `DarkLordExplosion2Vfx`, and `DemonKingImpactVfx` also request `PF_ExplosionDebrisBounce_HighArc` through `PresentationSpawnService` at the same world position. The authored HighArc prefab lives directly at `Assets/Resources/DemonKing/Vfx/PF_ExplosionDebrisBounce_HighArc.prefab`; do not keep a second mirror copy with separate particle tuning. It is visual-only and does not affect hit timing, fragments, SFX, or camera shake.
- Direct `DemonKingImpactVfx` commits should shake at the same commit point unless an existing timed-hit callback already owns shake. Bombardment release impact and EgoSword planting impact use dedicated shake hooks; ExplosionJump landing, WallBounceRush final landing, hand GroggyRecoverCounter, and EgoSword VerticalStrike should not add duplicate shake calls.
- DemonKing concrete one-shot VFX should own hit timing through `TimedAnimatedHitEffect2D` when the VFX exists as a generated Resources prefab. The builder adds `EnableHitCollision`/`DisableHitCollision` events and disabled trigger colliders to one-shot explosion/impact/slash/stab/release/sword-attack prefabs. Runtime code supplies the collider size, payload, shared-hit registry, and optional hit-window callback for sound/shake. Continuous body-contact dash/rush damage and laser active windows remain code-driven.
- DemonKing warnings should use `AttackTelegraphService` with `AttackTelegraphSpecUtility.WithThinWarningOutline(...)`; do not add separate primitive red square/circle warning duplicates. DemonKing circular ground warnings route through the opt-in `AttackTelegraphSpec.CreateTopDownCircle(...)` 70% Y-scale helper for the top-down read. Non-collider overlap/fallback damage paths that are paired with selected top-down ellipse warnings use `TopDownEllipseHitUtility2D` / `DemonKingCombatUtil.ApplyTopDownEllipseDamage(...)` for final filtering, while authored `TimedAnimatedHitEffect2D` collider paths continue to use prefab collider shapes and animation-event timing. Unselected `CreateCircle(...)` warnings and `CreateRing(...)` warnings remain visually circular. Primitive visuals are still allowed as fallback active attack flashes when an authored VFX prefab is missing.
- DemonKing pattern speech is fired from pattern `AbilityLogic` start/warning timing through `BossSpeechController`. Main-body speeches use the boss speech anchor, while EgoSword throw/recall/dropped subpatterns use `EgoSwordActor` world-position resolvers so inactive held sword, throw-origin socket, fixed dropped sword, and recalling sword positions can all host separate pooled bubbles without replacing the boss bubble. For sword-related patterns, DarkLord and EgoSword use separate `BossSpeechSituationEnum` values: the `DemonKing*` situation is the DarkLord/body line, and the `EgoSword*` situation is the sword-position line.
- Pattern SFX and camera shake are owned by the pattern AbilityLogic or side actor that knows the commit timing. Shake should be called from actual hit/explosion/landing callbacks, not warning start or loop VFX updates. Clustered explosions should share a hit registry and group presentation where the pattern releases several hit VFX at the same timing.
- DarkLord/DemonKing root body SpriteRenderer should stay on `Entity / Order 0`. Do not raise the body to Projectile for focus effects; use Flowering-style world dim under Entity (`Entity / Order -1`) and keep EyeFlash/GroggyRelease/attack VFX on Projectile so they draw above the body.
- HeavySlash treats `stopBeforeTargetDistance` as first-approach spacing only. After that approach, it holds `Slash_1`, tracks for `2.0` seconds with the sector positioned so the live player sits at `playerAnchorInWarningRadius` of `slashRadius`, and computes the commit root position so `SwordSlashOrigin` will land on the locked sector origin. It then freezes the sector for the final lock-on blink window, performs a short DashStab-style afterimage lunge to the locked commit position, samples `Slash_2`, and holds that pose after the hit.
- HP50 `WallBounceRush` owns per-rush `DemonChargeEffectVfx` visuals as one prefab/controller instance: the rush plays `Loop`, then `chargeDisappearStartProgress` detaches the same instance and plays `Disappear` before the endpoint pause. Missing/zero progress values are treated as `0.9` to protect older AL assets from immediate disappear playback, and `chargeVfxFlipX` controls the Charge VFX horizontal flip. EgoSword throw/recall owns `SwordSpin4Frame` as a position-following visual that intentionally does not inherit the sword's rotation.
- DemonKing body pattern animation starts are guarded per pattern execution only for single-commit motions. Do not apply the once-per-pattern guard to multi-hit or multi-rush clips such as DashStab; those must be allowed to restart per strike. Use last-frame hold/sample helpers for impact and recover frames that intentionally re-sample a clip frame.
- Same-state pose holds are guarded separately from start playback: Groggy eye-flash holds freeze the current Groggy frame when already active, and `Slash`/`GroggyCounter` last-frame holds do not call `Animator.Play(...)` again if the current state has already reached the requested frame.
- `DarkLord_Sword_Throwing` is a two-second non-loop clip: frame 0 holds for `1.5` seconds, then frame 1 holds for `0.5` seconds. Its clip sample rate is `2` so `ResolvePatternAnimationLastFrameStartDelay(...)` still resolves the throw commit to the frame-1 start at `1.5` seconds.
- `DarkLord_Sword_Slash` is frame-controlled by HeavySlash: frame 1 is held during warning/prep, then the last Slash frame is sampled at the actual Slash hit-window callback and remains visible through the clip/end-pose hold.
- HomingMagic stock orbs are visual-only ammo above the boss. Each shot owns a live straight aim warning from the selected stock orb until projectile release, then consumes that stock orb and recenters the remaining visuals.
- SwordThrow starts `DarkLord_Sword_Throwing` immediately and uses the clip's last-frame start delay as the EgoSword release moment. Only the first throw has the aiming line; wall reflections stay physics-only.
- DashStab has a three-beat body rhythm per attack: `DarkLord_Sword_DashStabReady` during warning/prep, `DarkLord_Sword_DashStab` during each rush movement, then `DarkLord_Sword_DashStabReady` again for the recover/end pose hold. PierceCombo uses this rhythm for all three attacks instead of treating DashStab as one clip start per pattern. Each Pierce warning tracks the live target first, then `lockOnSeconds` freezes the final warning line with blink styling before the DashStab commit.
- Hand-state jump attacks hold the first `DarkLord_Hand_JumpAttack` frame during root-position travel, then switch to the last frame exactly at the landing damage/VFX commit. The travel uses a Slime Knight-style rhythm: quick move/up to the target, high hold, then a near-vertical final drop. This is a DemonKing-root movement solution; a separate visual-root jump would require prefab structure work.
- `DarkLord_Hand_GroggyCounter` is the hand-state groggy counter pose and is also used once before line Bombardment starts spawning its repeated lane explosions. Bombardment waits for the second GroggyCounter frame, spawns `DemonKingImpactVfx` at the boss, holds that release frame for about `1` second, then returns the body to `DarkLord_Hand_Idle` while the lane explosions proceed. `DarkLord_10Percent` is held after FinalDesperation reaches the arena center.
- Bombardment moves the DemonKing to the side lane setup point, then turns back toward the arena center/explosion lane before the release pose and repeated lane explosions so the body does not perform the pattern with its back to the active explosions.
- `DarkLord_Sword_GroggyCounter` is the sword-held groggy counter pose and intentionally uses only `DarkLord_Sword_Slash_0`. GroggyRecoverCounter sequence is Groggy pose during the eye-flash beat, then GroggyCounter at the impact frame, then current combat idle after the impact hold. Sword-held counters use `DarkLordGroggyReleaseVfx`; hand-state counters use `DemonKingImpactVfx`. It should not oscillate back to Groggy between the counter frame and idle recovery.
- Pattern motion windows acquire a DemonKing face-target lock so the shared auto-facing update does not flip the body toward the player while an authored attack pose is playing. Pattern code may still set facing once at a warning or attack commit boundary.
- HomingMagic uses `DarkLord_Hand_Balt` frame control directly: first frame for projectile creation, last frame held through the fire/dash follow-through. It can optionally show `projectileCount` visual-only stock orbs above the boss through `stockOrbVisualPrefab`, arranged in a recentered arch. Each shot consumes the target-side outer stock orb first and spawns the real `DemonKingProjectile2D` from that world position. `firedProjectileVisualPrefab` is a separate child visual on the projectile root; if serialized slots are unset, the Resources wrappers generated from `HomingMagicBaltVFX.anim` and `HomingMagicBaltProjectile.anim` are used. If those prefabs are also missing, stock display is skipped and the old purple primitive projectile renderer remains the fired fallback.
- `Tools/DemonKing/Visual Tuning Preview` now has a Pattern Workbench for `AL_DemonKing_*` assets. It builds an Editor-only synthesized timeline for each DemonKing pattern, showing body pose, VFX, socket marker, warning/hit shape, EgoSword marker, and pattern policy notes together in the Composite preview. It is an authoring aid, while the Play Mode-only Actual Pattern Runner can execute the selected AL through the live DemonKing `AbilitySystem` when exact runtime socket/VFX/warning/movement behavior must be checked. The same panel can optionally render the live Play Mode DemonKing/target scene into the Preview Window, so designers can compare runtime execution without switching focus away from the Workbench. Test controls can run the selected pattern once or loop it, temporarily suppress the normal DemonKing combat loop so only the selected AL runs, add a temporary `State.Invulnerable` tag to the player without locking input, move the player to the arena center, and refresh terminal test state after patterns such as FinalDesperation. Pattern policy values and presentation mappings that designers need to tune should remain on the owning AbilityLogic asset; examples include Bombardment release impact hold, GroggyRecoverCounter dim/eye-flash/impact-hold ratios, ExplosionJump/WallBounceRush jump motion profiles, HeavySlash/Bombardment/FinalDesperation explosion cue refs, and WallBounceRush charge/final landing cue refs. If a pattern phase visibly changes the DemonKing body pose, the phase should either reference an editable `DemonKingBodyAnimationRef` field or be explicitly empty/no-override; VFX placement remains `DemonKingVfxCueRef`/socket-owned rather than body-animation socket-owned.
- DemonKing keeps `State.Status.KnockbackImmune` active through its lifecycle so player knockback effects can damage it without displacing the boss root.
- HP50 `WallBounceRush` uses linear rush movement to a wall-safe endpoint, starts the Charge `Disappear` state at the configured travel progress before endpoint arrival, pauses at least `0.1` seconds at each endpoint, then recalculates the next rush direction from the current target. Endpoint casts prefer the optional `DemonKingController.wallRushCollisionProbe` collider before falling back to body-radius CircleCast. If the direct player path is shorter than the minimum visible rush distance, the pattern tests nearby player-facing angles and chooses the longest visible candidate before consuming that rush beat. The warning line uses the same selected endpoint as the movement. The pattern is hand-only visually because selection forces `ThrowEgoSword` first when the sword is held; do not branch back to sword DashStab/DashStabReady inside the charge sequence.
- 10% `FinalDesperation` captures the center position before the attack loop, keeps laser/bomb logic on that center, applies only a small root transform Y floating offset for body presentation during the loop, renders final laser VFX behind the `Entity / Order 0` body through an AL-owned sorting override, and places EgoSword in a visual-only planted state in front of the boss.
- Boss death no longer hides EgoSword immediately. `DemonKingController` asks `EgoSwordActor` to run a no-effect/no-afterimage cinematic death plant in front of the boss facing direction; normal battle cleanup still hides the sword on destroy/disable.
- `DemonKingVfxCueRef.scale` is a runtime size multiplier for cue-authored VFX. Built-in GroggyRelease uses branch cue size/scale, while built-in Impact keeps authored prefab scale unless the cue explicitly provides size or scale.
- DarkLord/DemonKing body sprites are authored facing left by default. DemonKing does not use the shared `Enemy` right-facing baseline helper for body facing; in `DemonKingController`, `flipX == false` means facing left and `flipX == true` means facing right. Keep auto-facing, pattern-facing, `FacingDirection`, and sword hold offset mirroring on that same baseline.
- DemonKing death pose is `DarkLord_Hand_Groggy`, played directly from `DemonKingController` so it can still be sampled after `IsDead` blocks normal pattern animation playback.
- `EgoSwordActor` held state remains hidden body-animation-only, but throw/recall tuning is now Inspector-facing through local throw origin offset, local recall target offset, initial throw/recall rotation fields, recall lift height/time, recall lift hold, and minimum visible return time. Throw and return prefer `DemonKingVfxSocketMap` sockets (`SwordThrowOrigin`, `SwordThrowReturnOrigin`) with those offsets as fallback. Recall starts with the sword lifting and hovering briefly, then enables `SwordSpin4Frame`/afterimage only for the visible return flight to the DemonKing socket.
- DemonKing/EgoSword speech keeps the existing `BossSpeechData` situation-to-random-lines schema. ThrowEgoSword plays DarkLord's `DemonKingThrowEgoSword` and EgoSword's pre-release `EgoSwordThrowEgoSword` at the throw-origin resolver with a duration clamped before release, then plays `EgoSwordThrowEgoSwordRelease` from the live sword resolver immediately after `sword.Throw(...)`; the release bubble can optionally use the sword rotation resolver through the `rotateReleaseSpeechWithSword` AL toggle, which defaults off so the bubble stays upright unless explicitly enabled. ## Ownership And Lifecycle

- Boss controllers own boss battle runtime; boss encounter setup and boss battle-end results should remain visible as separate flow boundaries.
- Boss terminal ending is opt-in per selected boss through `BossDefeatEndingSequence`. `BossDeathPresentation` acquires `DialogueService` non-dialogue UI suppression before the death SpeechBubble, keeps Gameplay HUD/Boss HUD hidden through SpeechBubble, terminal Dialogue, outro, and Title transition startup, removes the letterbox before terminal Dialogue starts, keeps the camera focused on the boss through terminal Dialogue/outro, and restores camera/UI only on incomplete terminal handoff. `BossDefeatEndingSequence` revalidates a playable `EndingOutroPlayer` immediately before the outro, lets `EndingOutroPlayer` recover a live `EndingOutroView` from the active `GlobalUIRoot`, keeps player cinematic protection through the outro and accepted TitleScene transition startup, then ends the run as Victory and requests `TitleScene` through terminal-flow fade-out and TitleScene fade-in durations. This terminal path suppresses normal reward-ready, chest, and portal handling.
- `EndingOutroView` owns a runtime-closed startup state for globally authored fullscreen outro roots. If the shared `IntroOverlay` is left active in `GlobalUIRoot` for editing, the view hides itself on startup; real playback activation through `Show(...)` is explicitly exempt so inactive authored roots still play normally.
- Normal boss reward chests own their dust-only reveal through `TreasureChest.PlayRewardReveal()`, which plays one configured reward dust ParticleSystem at a chest-local anchor/offset after loot initialization. Normal boss reward portals can opt into `BossRewardObjectRevealPresentation`; the battle-end handlers call it only after portal visibility restoration succeeds, and without that component the portal appears immediately as before. Gate reveal authoring should wire a scene-local reveal root, target SpriteRenderers, particle prefab/scene references, spawn anchor/offset, and colliders to lock interaction until the reveal finishes. A serialized SpriteMask is optional; if missing or parented under the moving reveal root, runtime creates a fixed playback mask from the configured mask or first target renderer. Portal reveal sub-effects now share one reveal timeline: mask/collider lock spans the reveal, loop dust and loop/root shake run during the reveal, burst dust and the stronger completion camera shake run only when the reveal reaches the final position. Particle prefab spawn pose is still resolved from the final reveal-root position, so the selected-object particle gizmo marks the actual authored output point even though playback starts after the root is lowered. Gate reveals can also use the component's portal-only polish fields for repeated small camera shake during the rise, a stronger completion shake, and local reveal-root tremble. In `GlobalVisionMaskRoot` scenes such as `HeoMinSeok_Boss_Shadow`, portal reveal should keep `isolateGlobalVisionMasksDuringReveal` enabled so eligible scene vision masks can be temporarily narrowed to the dark overlay sorting range without rewriting player-following `PlayerVisionMaskFollower` masks; the option defaults enabled but only runs when the reveal has a local mask or masked renderers. The target scenes `HeoMinSeok_Boss_Shadow`, `HeoMinSeok_Boss_Dragon`, and `SangHyup_Boss_SlimeQueen` can use `Tools/Validation/Apply Boss Reward Reveal Target Scene Setup` for a first-pass scene-instance setup. The apply defaults are currently based on the tuned `HeoMinSeok_Boss_Shadow` reward objects: chest dust prefab `ChestReavealDust`, chest dust offset `(0, 0, 0)`, gate start offset `(0, -2.95, 0)`, gate particle offset `(0, -1.5, 0)`, reveal duration `1.5`, completion shake amplitude `2`, and root tremble amplitude `(0.5, 0.038, 0)`.
- Slime Queen variants (`SlimeQueen`, `SlimeQueenP2Short`, `SlimeQueenP2Long`) inherit common groggy/stagger support from `SlimeQueenBossBase`. The base ensures a runtime `StaggerGaugeSystem` when the prefab does not author one, resolves the shared stagger attributes from the boss `AttributeSet`, and uses a 3-second status-only Groggy effect that grants `State.Status.Groggy`. Phase two Short/Long bodies use the common boss HUD registration path as independent slots, so the HUD no longer needs Slime Queen concrete references or dual-channel source adapters. Slime Queen speech text/theme is shared through `SlimeBossSpeechData.asset` and the base speech helper; P1/P2-specific durations, offsets, callbacks, split timing, and finale flow remain owned by the Slime Queen controllers instead of `BossSpeechController`.
- Slime Queen phase two drain interaction is owned by `DrainPipe`, not by the phase-two boss controllers. Broken drains keep Pawn slime suction on `suctionRadius`, while P2 Slime Queen acquisition uses the separate inspector-authored `phaseTwoBossSuctionRadius` and selected-object gizmo. When a P2 boss enters that radius, `DrainPipe` locks the boss through `SlimeQueenPhaseTwoBase.BeginDrainControlLock()`, temporarily disables the boss `MovementMotor2D`, directly pulls the boss to the drain, keeps it submerged for 4 seconds, restores movement/control, then resets the drain to its original cork state with hit count `0`. While drain-locked, `SlimeQueenPhaseTwoBase.Update()` returns before the shared pit-fall lock can call per-frame `StopAllMotion()`. P2Short owns a concrete `isSinking` Animator bool hook; P2Long has a safe hook that no-ops until the bool is authored on its controller. Do not reuse the broad Pawn suction radius for P2 boss acquisition, do not let normal boss movement own the drain-pull step, and do not convert P2 drain completion into permanent drain blocking.
- Slime Queen slam-style movement is shared through `SlimeQueenBossBase.ApplyKnightStyleSlamPose(...)`. P1 random jump, P2Long random jump, and P2Short repeated slam should use that helper so their motion matches Knight slime's fast move-to-warning, hover, and final drop rhythm instead of reintroducing local sine-arc movement.
- P2Short toxic rush has only three intended stop conditions: wall collision, normal `HoleTrap` fall, or player collision. It builds the rush segment from a long wall cast using `toxicRushWallLayers`; `SlimeQueenRandomMoveBounds` is not a toxic-rush range limit. If P2Short falls into a normal `HoleTrap` during toxic rush, `PitFallExecutor` notifies `SlimeQueenBossBase` pit-fall start/completion hooks, and `SlimeQueenP2Short` consumes that state after respawn to play the center Knight-style slam plus the `SlimeQueenToxicRushPitFallSlam` speech entry. Player collision and wall collision must not trigger that center slam. DrainPipe sinking does not use this HoleTrap completion path.
- Boss encounter presentation owns its own UI input block through `GameFlowInputBlocker` while camera focus, dialogue, and return-to-player handoff are running. Dialogue still owns only dialogue playback blocking.
- Boss encounter presentation also owns player visual-facing locks while the intro sequence is active. `BossEncounterDirector`, legacy `BossTalkManager`, and `TutorialBossEncounterSequence` acquire owner-token locks on `PlayerAnimatorController2D` and `WeaponPresentationRig2D` so the player body and weapon presentation do not continue following cached Aim during the encounter. `PlayerCinematicProtection` remains the input/invulnerability owner; do not make every cinematic protection flow freeze facing unless that flow explicitly needs it.
- General mobs are spawned through population systems, then stay battle-ready through their own runtime FSM. Do not treat all mob work as encounter work.
- Spawn systems own instantiation/configuration and may bridge to lock overlays, but lock semantics are not the same as spawn semantics.
- `ChestMonsterKillLockNavigationView` is presentation-only: it reads alive registered monsters from `ChestMonsterKillLock`, spawns authored arrow prefabs locally, and must not decide unlock, spawn, or combatant counting rules. The authored arrow prefab is SpriteRenderer-only; avoid renderer-driving scripts and MeshRenderer/MeshFilter presentation for this 2D guidance. Its selected-object gizmos are authoring/debug visualization only.
- `RoomEnemyNavigationOverlay` is also presentation-only: one scene-level overlay listens to `MonsterSpawnRoomGroup.ActiveRoomEntered/ActiveRoomExited`, reads `GetAliveRegisteredMonstersNonAlloc(...)`, and pools the same SpriteRenderer arrow prefab. It hides while no room is active, above its threshold, after clear, on room exit, or when an individual target is already in the camera viewport. Camera-edge placement is computed in viewport space through `CameraBootstrap.GetMainCamera()` with `Camera.main` fallback.
- Puddles/hazards are battle environment systems and should stay separate from boss-specific policy unless the boss ability owns only a trigger.
- `PitFallExecutor` opens a mob pitfall death resolution window before applying trap damage and keeps it active through pitfall completion handling. General `Mob` death skips monster loot during that window, and `Slime` uses the same window to mark pitfall death before HP damage can synchronously trigger normal split logic.
- Enemy cleanup rules should follow `Docs/Contracts/MobCleanupContract.md` when general mobs are involved.
- Shared enemy player targeting should resolve to the canonical player root through `PlayerRuntimeRegistry`/`PlayerInteractor2D`; player-attached orbit/effect colliders or directly assigned child transforms should not become the boss target transform.
- Shared mob perception treats a closed `DoorObject` on the enemy-target sight line as a blocker for acquisition, chase, common attack continuation, and Dead's Skeleton self-destruct flow.
- DemonKing-owned side actors must stop with the DemonKing battle lifecycle. `EgoSwordActor` has an explicit battle-end cleanup path that cancels active dropped GAS subpattern tokens, stops its independent loop, clears mask/aura/attached VFX, marks the runtime sword held, and deactivates the authored sword actor. A new fight starts with the held sword hidden; the actor is reactivated only by the throw commit path.

## Lock Count Policy

- Spawn-registered combatant roots create one room/chest unlock tracking unit.
- Slime split descendants are the special split exception: they inherit the parent's room/chest lock tracking unit and keep that one count alive while any descendant is alive, but their runtime no-loot marker suppresses normal monster drops.
- General direct summons are not lock targets. This includes boss/local summons that instantiate enemies without the room spawn registration path.
- Runtime boss/local summoned mobs, such as SlimeQueen summoned slimes and Witch retreat skeletons, suppress normal monster loot even when they use the regular mob death flow.
- Transform or phase changes on the same tracked GameObject are the same enemy for lock purposes.
- Death presentation still counts as alive while the tracked unit has a live representative. The lock releases only after the tracked unit compacts to no living member.
- No-loot/gimmick enemies count only when they entered the lock through the spawn registration path or an explicit Slime split inheritance path.

## Known Pitfalls

- Boss-specific states, actors, and ability logic are mixed by boss; do not move them without prefab/scene reference checks.
- Pattern presentation ownership should follow `Docs/Contracts/PresentationAuthoringContract.md`.
- The former `BossDrop` legacy reward flow is resolved in `Docs/RefactorBacklog/BossDropResponsibilitySplit.md`; unhandled reward/portal authoring now reports editor/development warnings through `BossRewardFallbackService` instead of running a dynamic fallback.
- If a normal boss direct-scene Play looks like final-route behavior, check `RunRouteCatalog.asset` and the `BossEncounterEndDirector` debug route context first. A development plan with only the current RouteSet makes the tested scene both first and last; direct Play should seed the full catalog and report `IsFinalRouteSet=False` for `HeoMinSeok_Boss_Shadow`, `HeoMinSeok_Boss_Dragon`, and `SangHyup_Boss_SlimeQueen`.
- Chest reward reveal does not use `BossRewardObjectRevealPresentation`; it depends on `TreasureChest` reward dust fields. `BossRewardObjectRevealPresentation` is portal reveal presentation and does not discover reward objects globally; it still depends on serialized component references on the scene portal object. If renderer, particle prefab/scene reference, spawn anchor, or collider fields are empty, the corresponding portal reveal/mask/dust/interaction-lock behavior will be missing until the scene instance is wired in Unity. The selected-object gizmos show portal particle spawn position, runtime/reveal mask position, reveal start/end points, and masked renderer start/end bounds for tuning. `TreasureChest` selected-object gizmos show the chest reward dust spawn point. The target-scene apply tool supplies first-pass TreasureChest dust fields, portal references, and portal shake settings, but generated mask bounds/sorting, dust offsets, reveal offset, shake strength, and collider lock feel still need Scene/Game view review.
- If a boss reward chest appears inactive while the portal appears, first confirm whether the tested scene is actually a final-route-suppressed clear. `HeoMinSeok_Boss_Shadow` direct scene testing is not final-boss suppression, so next confirm the watched object is the same `TreasureChest` instance referenced by `BossEncounterEndDirector` or the active `BossBattleEndHandler`; duplicate scene chests with similar names can make the wrong object look like the reward failed. `BossRewardSpawnService` activates the referenced chest before boss loot generation so later loot exceptions do not keep the object hidden, but Console logs such as `[BossBattleEnd] ActivateTreasureChest failed.` still need investigation because they can leave boss-specific contents or physical drops incomplete.
- Dust-only chest reveals should not carry `BossRewardObjectRevealPresentation`; rerun the target-scene apply tool to remove stale chest reveal components and configure `TreasureChest.rewardRevealDustParticle` instead. Gate reveal masks must not move with the same transform used as `revealRoot`; leave the mask field empty for runtime mask generation or author it outside the moving root. Particle fields may reference scene ParticleSystem instances or ParticleSystem prefab assets; prefab assets are instantiated at their configured spawn anchor plus local offset. If a loop dust scene ParticleSystem is authored under the moving reveal root, the reveal component temporarily detaches/restores it during playback so ground dust timing and position follow the reveal timeline instead of inheriting the lowered gate motion.
- Unity SpriteMask targeting is sorting-range based, not per-mask. If a scene has `GlobalVisionMaskRoot`, a portal renderer using `VisibleInsideMask` for its local gate reveal can also be clipped by global vision masks. Keep portal reveal isolation enabled in those scenes, skip player-following `PlayerVisionMaskFollower` masks during isolation, and verify the dark overlay cutout plus portal reveal together in Play Mode.
- Do not add `BossDefeatEndingSequence` as a common boss prefab default. It is a terminal story flow and should be assigned only to the specific boss scene/object that should end the run.
- Terminal ending outro UI is authored scene/prefab UI driven by `EndingOutroView`; do not create Canvas/TMP/Image hierarchy at runtime for final presentation.
- Terminal ending Victory GameOver must capture pending magic stone gain before `EndRun(Victory)`. The run commit belongs to the GameOver return button so the display amount and inventory inspection still see the current run state.
- Terminal death no longer lets the letterbox own HUD fading. `DialogueService` owner-token suppression owns Gameplay HUD/Boss HUD visibility from death SpeechBubble through terminal Dialogue and outro so HUD is not restored in the Dialogue-to-outro gap.
- Keep the final black fade before `TitleScene` on `BossDefeatEndingSequence.titleSceneFadeOutDuration` and the TitleScene reveal on `titleSceneFadeInDuration`; do not globally slow `SceneFadeTransitionService` unless all transitions from that scene should change.
- If the final terminal outro slide appears to wait and then cuts to `TitleScene` without a visible fade, check whether the shared `SceneFadeTransitionService` fade image is rendering behind the authored outro UI or the destination scene's canvases. The service brings its overlay root to the last sibling and temporarily elevates the overlay canvas while active, and `SceneTransitionCoordinator` re-resolves a replacement fade service after load if the original transition service was destroyed. Do not add outro UI after the fade image and then bypass the service activation path.
- If terminal ending outro is skipped after entering the boss scene from Hub/Corridor, first check whether the assigned `EndingOutroPlayer` recovered a live `EndingOutroView` from the active persistent `GlobalUIRoot`. Direct scene play can hide stale-reference bugs because the scene-authored `GlobalUIRoot` is the first live root, while cross-scene entry destroys the duplicate root and any serialized view reference under it.
- The boss battle-end migration validator can find missing scene `BossBattleEndHandler` coverage, missing authored chest/portal references, optional RouteSet special reward presets, stale deleted component/catalog GUIDs, stale definition/profile fields, and boss exit portal semantic mistakes. Scene Auto Fix can create first-pass handler/boss wiring, but final chest and portal objects must be placed and assigned in the Inspector.
- `RoomDoorMonsterKillLock` and `ChestMonsterKillLock` track registered lock units. Do not infer lock participation from enemy type alone; use spawn registration or Slime split inheritance.
- Pitfall damage can synchronously enter enemy death through the GAS attribute callback. Any death-result classification that affects loot, Slime splitting, summons, or lock-sensitive behavior must be set before applying pitfall damage, not only in the later pitfall completion callback.
- KillLock chest navigation arrows follow the live representative of each registered lock unit, so delayed destruction or split descendants keep arrows visible until the unit has no living member.
- Room enemy navigation arrows follow the active `MonsterSpawnRoomGroup` lifetime. If a scene has room groups but no `RoomEnemyNavigationOverlay` or no arrow prefab reference, enemy guidance will not appear even though door lock behavior still works.
- `FirePuddleArea` has boss-specific target exclusion logic. If more hazard actors learn boss policy, move the rule toward a combat target policy instead of spreading concrete boss checks.
- Do not add new concrete boss type branches to common Boss HUD for split or multi-body bosses. Add a boss-specific HUD source/adapter instead.
- Player-attached relic/effect objects should avoid unintended `Player` tags, hurtboxes, or blocking body colliders. The shared `Enemy` target resolver maps player-owned child colliders and assigned child transforms back to the player root, but collision/hurtbox authoring still needs separate review.
- Closed-door perception depends on `DoorObject` colliders being authored on the physics line between enemy and player. If a closed door is visual-only or on an ignored collider setup, mobs may still perceive through it.
- DemonKing EgoSword laser clips bind to the local SpriteRenderer on the Start/Body child objects. Keep Animator components on those child objects with Start/Idle/End states; root-level `AnimationClip.SampleAnimation(...)` is not the supported playback path for this VFX.
- DemonKing non-laser sprite VFX controllers must stay valid Unity YAML. If a controller contains `m_TimeParameter:---` or any `:--- !u!` sequence, Unity may fail to import/play the Animator state and the VFX will appear invisible even though the prefab loads.
- If non-laser DemonKing `.anim` or `.controller` assets appear empty in the Unity Inspector, use `Tools/DemonKing/Rebuild Pattern VFX Assets`. The builder uses UnityEditor `AnimationUtility`, `AnimatorController`, and `PrefabUtility` APIs instead of relying on handwritten YAML; `EgoSwordAttackAura` is generated as EgoSword state clips/controller only, not as a spawned VFX prefab.
- DemonKing non-laser VFX fallback can also be caused by state validation, not asset absence. Unity Animator state checks should accept layer-qualified hashes such as `Base Layer.Play`, and missing `Resources` loads should not be cached across play sessions while art assets are being imported.
- DemonKing EgoSword laser warning and attack lines intentionally use different geometry. Do not reuse the warning `LaserLine` for attack VFX/damage unless the design changes back to wall-blocked lasers.
- `laserVfxRayOriginOffset` is a visual-only offset for the animated ray start points. It does not move warning geometry or damage rectangles.
- EgoSword buried presentation is runtime mask presentation only. It should be cleared before sword travel/recall/disable and before VerticalStrike hover tracking so temporary VFX children are not accidentally masked.
- DemonKing authored phase data and runtime-generated fallback data are separate paths. If the scene has `AD_DemonKing_*` phase entries, keep `configureRuntimePatternsOnStart` off; otherwise the controller will generate temporary abilities and hide the Inspector configuration at runtime. Phase abilities are registered by `BossControllerBase`, so `AbilitySystem.initialAbilities` should remain empty for these patterns.
- EgoSword dropped VerticalStrike and CrossLaser are DemonKing-owned GAS abilities even though their cadence is separate from the main boss pattern timer. Keep them `ParallelIndependent`, register them through `DemonKingController`, and do not move their timing back into direct actor-only coroutine attacks.
- EgoSword dropped loop gates must check both sword state and owner lifecycle. Wait intervals, activation gates, and active subpattern cancellation should require `state == Fixed`, `owner.IsCombatActive`, and `!owner.IsDead`; otherwise the sword can continue attacking after the boss fight has ended.
- DemonKing 50% `WallBounceRush` must run with `SwordMode == Drop`. If HP crosses the 50% gate while the sword is held, pattern selection must force `ThrowEgoSword` first and defer `WallBounceRush` until after the throw commits. The charge body animation path is therefore hand-only.
- If a KillLockDoor closes before the player crosses the threshold, first inspect `PF Player` `PlayerInteractor2D.bodyCollider` wiring to the `BodyCollision` `CapsuleCollider2D` and the room trigger shape. `RoomEncounterEntryTrigger2D` intentionally waits for strict bounds-sample containment, so narrow or concave room triggers can close slightly later than visual capsule contact.
