현재 변경사항 및 사용법, 유의사항

현재 변경사항

- 프로젝트 문서 체계가 단순 작업 로그에서 프로젝트 메모리 구조로 확장되었습니다.
- 새로 추가된 문서 영역은 Docs/StructureMemory/ 와 Docs/RefactorBacklog/ 입니다.

Docs/StructureMemory/

- 빠른 구조 파악용 문서입니다.
- 공식 기준 문서는 아닙니다.
- 다음 작업자가 해당 시스템을 다시 분석하는 시간을 줄이기 위한 구조 지도입니다.
- 현재 UIFlowInputBlocking.md 가 추가되어 있습니다.

Docs/RefactorBacklog/

- 구조적 부채와 리팩토링 후보를 기록하는 문서입니다.
- 단순 TODO가 아닙니다.
- 왜 문제가 되는지, 목표 구조가 무엇인지, 언제 리팩토링할지를 기록합니다.
- 현재 BossDropResponsibilitySplit.md 가 추가되어 있습니다.

기존 문서 역할

- Docs/SessionLogs/YYYY-MM-DD.md: 그날 실제 작업 기록입니다.
- Docs/ErrorLog.md: 재발 가능한 실수와 방지 규칙입니다.
- Docs/DecisionLog.md: 오래 유지할 설계 결정입니다.
- Docs/Architecture/: 안정화된 공식 구조 문서입니다.
- Docs/Contracts/: 반드시 지켜야 하는 lifecycle, cleanup, authoring 규칙입니다.
- AGENTS.md, Docs/README.md, Docs/Overview/document-inventory.md 도 새 문서 체계를 찾을 수 있도록 갱신되었습니다.

작업 시작 시 읽는 순서

- 1. Docs/CurrentTask.md
- 2. Docs/ErrorLog.md
- 3. Docs/DecisionLog.md
- 4. Docs/README.md
- 5. Docs/README.md 가 안내하는 task-specific 문서

예시

- UI 입력 차단, Dialogue, Chest, Upgrade, Reward 흐름을 만질 때는 먼저 Docs/StructureMemory/UIFlowInputBlocking.md 를 읽습니다.
- BossDrop, 보스 보상, 보스 포탈, 보스 타이머 쪽을 만질 때는 먼저 Docs/RefactorBacklog/BossDropResponsibilitySplit.md 를 읽습니다.

문서 갱신 기준

- 작은 버그 수정이나 단일 파일 수정은 보통 SessionLogs 만 갱신합니다.
- 여러 파일에 걸친 구조나 lifecycle이 바뀌면 StructureMemory 갱신을 고려합니다.
- 재사용 가능한 컴포넌트나 서비스가 생기면 StructureMemory 갱신을 고려합니다.
- MonoBehaviour, ScriptableObject, prefab-facing 구조가 바뀌면 StructureMemory 갱신을 고려합니다.
- 다음 작업자가 날짜 로그만 보면 맥락을 다시 파악하기 어려우면 StructureMemory 갱신을 고려합니다.

RefactorBacklog에 기록할 상황

- 빠르게 구현해서 책임이 한 컴포넌트에 몰린 경우
- legacy adapter가 남은 경우
- prefab 또는 scene reference 때문에 바로 제거하지 못한 경우
- 목표 구조는 알지만 이번 작업 범위 밖이라 미룬 경우

ErrorLog와 DecisionLog

- 재발 가능한 실수는 ErrorLog에 기록합니다.
- 오래 유지할 설계 결정은 DecisionLog에 기록합니다.
- 단순 실패 로그나 일반 TODO는 ErrorLog에 넣지 않습니다.
- 아직 실험 중인 구조는 DecisionLog에 확정된 것처럼 쓰지 않습니다.

Architecture와 Contracts 갱신 기준

- Architecture와 Contracts는 바로 수정하지 않습니다.
- 구조가 충분히 안정화되었고 앞으로 공식 기준으로 삼을 때만 갱신합니다.
- 갱신 전에는 Plan Mode에서 갱신 계획을 먼저 제안하고 승인 후 반영합니다.
- StructureMemory는 빠른 맥락 파악용입니다.
- Architecture와 Contracts는 공식 판단 기준입니다.

Plan Mode 사용 기준

- 앞으로 구조 변경 작업은 Plan Mode 위주로 진행하는 것이 좋습니다.
- 새 공용 컴포넌트나 서비스를 추가할 때는 Plan Mode를 먼저 사용합니다.
- 리팩토링을 할 때는 Plan Mode를 먼저 사용합니다.
- Architecture 또는 Contracts를 수정할 때는 Plan Mode를 먼저 사용합니다.
- MonoBehaviour, ScriptableObject, prefab-facing 변경이 있을 때는 Plan Mode를 먼저 사용합니다.
- 보스 보상, UI flow, Dialogue handoff처럼 여러 시스템이 얽힌 작업은 Plan Mode를 먼저 사용합니다.

Default Mode로 바로 처리해도 되는 경우

- 명확한 오타 수정
- 작은 null check
- 단일 파일의 좁은 버그 수정
- 문서 로그 보강
- 이미 합의된 구조 안에서의 단순 적용

UI 입력 차단 구조 사용법

- 현재 UI flow 입력 차단은 GameFlowInputBlocker가 담당합니다.
- UIManager는 중앙 정책 owner입니다.
- 각 기능 코드는 UIManager.SetExternalUiInputBlocked(...)를 직접 호출하지 않습니다.
- Flow owner는 GameFlowInputBlocker.GetOrAdd(this)로 blocker를 가져옵니다.
- 입력 차단이 필요한 구간이 시작되면 Acquire()를 호출합니다.
- 입력 차단이 끝나면 Release()를 호출합니다.
- 흐름이 자기 UI를 열어야 하면 TryPushOwnedUI(...)를 사용합니다.
- 이미 열린 stack UI의 시간 정지나 조작 잠금은 IStackableUI.GameplayLockProfile이 담당합니다.

GameFlowInputBlocker가 적용된 흐름

- 상자 첫 오픈
- Dialogue 진행 중
- Upgrade UI open fade
- Reward UI open presentation

UI 입력 차단 주의사항

- Chest의 world object 연출과 UI reveal 연출 타이밍은 섞지 않습니다.
- 다만 입력 차단은 상자 상호작용 직후부터 UI reveal 완료까지 이어질 수 있습니다.
- Dialogue 중 feature UI를 바로 열면 dialogue blocker에 막힐 수 있습니다.
- Dialogue 이후 feature UI를 열어야 하면 먼저 dialogue exit을 요청하고 blocker가 풀린 뒤 feature UI를 엽니다.
- Flow가 중단되거나 GameObject가 disable 또는 destroy 되어도 blocker가 남지 않도록 cleanup 경로를 확인해야 합니다.

BossDrop 관련 현재 상태

- BossDrop은 아직 완전히 제거된 구조가 아닙니다.
- 현재는 prefab 호환성을 위한 legacy adapter 또는 reference holder에 가깝습니다.
- RunProgressCoordinator는 보스 진행, RouteSet 완료, 타이머 정지를 담당합니다.
- BossRewardSpawner는 보스 보상 생성을 담당합니다.
- BossExitPortalActivator는 보스 처치 후 포탈 활성화를 담당합니다.
- BossDrop은 기존 prefab reference를 안전하게 유지하기 위한 임시 호환 경로입니다.

BossDrop 관련 주의사항

- 보스 보상은 StageLootTable과 LootManager가 기본값입니다.
- Affection, 업그레이드, 전용 보상은 기본 보상 위에 더해지는 additive modifier입니다.
- BossDrop과 새 컴포넌트가 동시에 잘못 연결되면 보상이나 포탈이 중복 처리될 수 있습니다.
- 보스 prefab이나 scene을 만지는 작업이 생기면 BossDropResponsibilitySplit.md 를 먼저 읽고 직접 wiring으로 이동할지 판단합니다.

검증 관련 주의사항

- Unity Editor가 열려 있으면 batchmode를 실행하지 않습니다.
- 코드 수정 후에는 먼저 정적 분석을 수행합니다.
- 기본 정적 분석 명령은 dotnet build CapstoneProject.sln --no-restore 입니다.
- 인터페이스, asmdef, MonoBehaviour, ScriptableObject, prefab 관련 변경이 있을 때만 Editor가 닫힌 상태에서 batchmode 컴파일을 제안합니다.
- 실제로 실행하지 않은 검증은 성공했다고 말하지 않습니다.

핵심 요약

- 최근 작업 기록은 SessionLogs에서 봅니다.
- 빠른 구조 파악은 StructureMemory에서 봅니다.
- 리팩토링 후보와 구조적 부채는 RefactorBacklog에서 봅니다.
- 반복 실수 방지는 ErrorLog에서 봅니다.
- 오래 유지할 결정은 DecisionLog에서 봅니다.
- 공식 구조 기준은 Architecture에서 봅니다.
- 반드시 지켜야 하는 규칙은 Contracts에서 봅니다.
- 공식 문서 갱신은 Plan Mode에서 승인 후 진행합니다.
