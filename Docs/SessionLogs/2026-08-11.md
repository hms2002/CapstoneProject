## Connected socket doors

### Changed

- Extended `DungeonRoomBuilder` to create exactly one Door prefab instance for every successful `DungeonSocketConnection`.
- Doors are positioned between the two adjacent socket-cell centers and rotated 90 degrees for left/right connections.
- Generated doors receive deterministic run-local IDs and use `DoorObject.DoorType.Normal` with `isPermanent = false`.
- Added generated-door cleanup so repeated generation clears both old Tilemap output and old door instances.
- Updated `ProceduralDungeonSceneInstaller` and `ProceduralDungeonV0Test.unity` with the shared `Door.prefab` reference and a dedicated `GeneratedDoors` root.

### Why

- A connection belongs to the assembled layout edge, so its door should be created once from `DungeonSocketConnection` rather than duplicated in both room templates.
- Keeping the initial door non-permanent matches the agreed rule that procedural corridor doors do not become permanently unlocked.

### Verification

- `dotnet build Editor.csproj -m:1 -nr:false` completed with 0 errors and 259 existing warnings.
- Unity batchmode regenerated the test scene and completed with return code 0.
- Installer verification confirmed 6 rooms, 5 connections, 5 generated doors, and `Normal`/non-permanent configuration for every generated door.
- The saved scene contains the shared Door prefab reference and dedicated `GeneratedDoors` Transform; generated instances are cleared before save so Play Mode rebuilds them through `generateOnStart`.
- Verification evidence is recorded in `Logs/ProceduralDungeonDoorInstall.log`.

### Remaining risks

- Interactive Play Mode still needs visual confirmation of prefab scale, sprite pivot, collider width, and interaction feel against the one-cell prototype socket.
- Generated doors currently open through normal player interaction; monster encounter close/reopen policy is not connected yet.
- Theme-specific door visuals are not part of `RoomThemeLibrarySO` in this slice.
