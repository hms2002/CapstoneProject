Why:
- The project goal is to split project-owned code into `Core`, `Gameplay`, `Infrastructure`, `Presentation`, `UI`, and `Editor` assemblies.
- Runtime/Core contained a direct `UnityEditor` menu tool, which blocks any clean runtime `Core.asmdef` migration.
- Runtime/Core also had an unnecessary DOTween source import in `AttributeValue`, which would have created avoidable asmdef reference pressure.
- `SoundRef` is serializable request data used by Core-owned ability/effect/cue assets, not the audio playback implementation. Keeping it under Infrastructure would force the future `Core.asmdef` to depend upward on Infrastructure.
- `SoundPlaybackContext`, `AudioHandle`, and `SoundPlaybackUtility` are the Core-facing audio request contract. Keeping the utility tied directly to `SoundManager` would keep Core dependent on Infrastructure.
- Camera shake, world presentation, damage popup, electric chain VFX, stagger head timer, player move input, and monster stage scaling all had Core callers holding concrete upper-layer or feature types. Each was converted to Core contract data/backend or moved into Core when the type is policy data.
- Current evidence shows most project-owned runtime code still compiles through default `Assembly-CSharp`, so a migration baseline is needed before adding asmdefs.
