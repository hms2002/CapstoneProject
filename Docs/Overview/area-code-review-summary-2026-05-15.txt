전체 문서 / 구조 작업 요약

- 프로젝트 소유 C# scripts를 Docs/StructureMemory 기준으로 지도화했습니다.
- Assets/Ink, Assets/Plugins는 외부/vendor 경계로 분리했습니다.
- ScriptSystemMap은 여러 단계로 확장했습니다.
  - 1차: 큰 script cluster
  - 2차: 책임 영역
  - 3차: 책임 단위 분해
  - 4차: hotspot 세부 분해
- 한 문서짜리 지도는 전체 인덱스로는 유용하지만, 프로젝트 규모상 모든 구조를
  한 문서 안에 유지하기에는 큽니다.
- 그래서 세부 구조 문서는 Docs/StructureMemory/ScriptSystems 아래로 분리했습니다.
- 반복 추가될 콘텐츠 제작 흐름은 Docs/Guides/ContentAuthoring 아래 별도 허브로
  분리했습니다.
- RefactorBacklog는 이후 P1/P2/P3/Blocked 기준으로 우선순위를 정리했습니다.


Weapon / GAS 리뷰

리뷰 범위:
- Weapon runtime / data / logic / equipment / interaction
- GAS runtime / effects / cues / tags / attributes
- Combat damage / hit / element / telegraph
- Player / status / movement 접점

핵심 결론:
- 말단 무기 구현부는 편의성과 특수성을 어느 정도 허용해도 됩니다.
- Lightning Spear가 크거나 고유 로직이 많은 것 자체는 문제가 아닙니다.
- 진짜 위험은 말단 무기 복잡도가 loadout, runtime data factory,
  processor factory, AbilitySystem 같은 상위 공용 구조로 새는 경우입니다.

구체 관찰:
- 무기 전용 로직은 weapon-specific AL / data / executor에 머물러도 됩니다.
- TrailPresenter처럼 관통 공격에서 재사용 가능한 조각은 Lightning Spear 의미에
  묶이지 않는다면 공용화할 수 있습니다.
- 지속 상태는 WeaponRuntimeData가 소유해야 합니다.
- 시간 경과 규칙은 WeaponRuntimeProcessor가 소유해야 합니다.
- Selection strategy는 상태를 읽기만 하고 mutation이나 cleanup을 하면 안 됩니다.
- 긴 실행과 취소/정리는 executor / runner 경로가 소유해야 합니다.

리스크 / 후속:
- WeaponRuntimeDataFactory와 WeaponRuntimeProcessorFactory의 예외 증가를 주시해야 합니다.
- 한 무기를 위해 AbilitySystem에 특수 예외를 추가하는 것은 피해야 합니다.
- 실제 파일 이동 전에는 prefab / scene / serialized reference 검토가 필요합니다.


Boss / Mob Encounter 리뷰

리뷰 범위:
- Boss FSM core, states, pattern selection/execution
- Witch, Slime Queen, Drunken Dragon, Demon King 말단 구현
- Mob FSM, ability coordinator, pattern runner, cleanup hook
- MonsterSpawner, room/chest lock overlay, hazards/puddles

핵심 결론:
- Boss와 Mob을 하나의 넓은 Encounter 묶음으로만 보면 책임 경계가 흐려집니다.
- Boss는 아래 흐름으로 읽는 것이 맞습니다.
  Encounter -> Battle -> BattleEnd
- 일반 몬스터는 아래 흐름으로 읽는 것이 맞습니다.
  Population / Spawn -> Battle Runtime -> Death Result

구체 관찰:
- 보스별 말단 파일이 큰 것은 그 자체로 문제가 아닙니다.
- 문제는 보스 고유 예외가 BossControllerBase, 공용 FSM, 공용 HUD, 공용 reward
  policy로 새는 경우입니다.
- 일반 몬스터는 이 게임에서 보통 Encounter 객체라기보다 MonsterSpawner를 통해
  배치/생성된 뒤 즉시 battle-ready 상태로 존재합니다.
- 몬스터 사망 결과와 room/chest lock tracking은 서로 달라질 수 있습니다.
- Slime 분열, 소환, 변신, 사망 연출 지연, 기믹 몬스터는 단순히
  "root object가 사라지면 클리어"라는 기준을 깨뜨릴 수 있습니다.

리스크 / 후속:
- Lock overlay count semantics는 기획 결정 전까지 blocked 상태입니다.
- split / summon / transform / death-delay 기준이 정해지기 전에는 lock refactor를
  만들거나 구현하지 않는 것이 맞습니다.
- BossDrop은 boss prefab reference가 migration되기 전까지 prefab-safe legacy adapter로
  유지됩니다.


Inventory / Chest UI 리뷰

리뷰 범위:
- Inventory stack / open / close
- Chest world object와 chest UI reveal
- GameFlowInputBlocker와 IStackableUI lock profile
- ItemSlotUI, ItemDragContext, detail panel, tooltip helper
- Runtime inventory, chest inventory, world drop, HUD projection

핵심 결론:
- 문제는 단순히 "MVP 패턴이 아니다"가 아닙니다.
- 구체 문제는 UI view/input script가 inventory transfer policy까지 알고 실행한다는
  점입니다.

구체 관찰:
- ItemSlotUI는 slot 표시와 pointer input을 담당하지만 quick move target도 판단합니다.
- ItemDragContext는 drag session state를 들고 있지만 drop, swap, relic merge,
  relic level preservation, rollback, failure behavior까지 처리합니다.
- PlayerInventoryPanelView와 ChestScreen은 UI-local container adapter를 정의합니다.
- HUD, tooltip, detail panel은 대체로 현재 상태를 표시하는 projection이라 우선순위가
  낮습니다.
- Tooltip 내용이 런타임에 바뀌는 것은 자연스럽습니다.
- 다만 전체 visual hierarchy fallback을 코드로 생성하는 것은 authoring 리스크입니다.

RefactorBacklog:
- InventoryTransferResponsibilitySplit

리스크 / 후속:
- 이 항목은 P1입니다.
- 새 inventory container, 새 item category, chest/world/equipment transfer 변경,
  inventory UI 이동이 생기면 coupling 비용이 커집니다.
- 실제 구현에서는 relic merge, relic level, rollback, warning popup 동작 보존이
  필요합니다.


Loot / Reward 리뷰

리뷰 범위:
- LootManager, LootPoolService, boss reward, chest reward, grave loot
- TreasureChest reward refresh / modifier behavior
- WorldItemPickup2D delivery
- ItemDatabase와 ItemManager

핵심 결론:
- 핵심 문제는 boss reward 구조가 아닙니다.
- BossRewardSpawner는 additive modifier 결정과 대체로 맞습니다.
- 더 큰 장기 리스크는 일반 loot / chest / world pickup 흐름입니다.
- reward roll, exclusion context, chest-specific policy, delivery 책임이 여러 runtime
  object에 암묵적으로 연결되어 있습니다.

구체 관찰:
- LootManager는 넓은 orchestration 지점입니다.
- LootPoolService는 여러 runtime source에서 exclusion context를 직접 만듭니다.
- TreasureChest는 chest refresh, modifier, relic level bonus, UI handoff를 함께 가집니다.
- WorldItemPickup2D는 presentation, interaction, 실제 item 지급, warning mapping,
  destroy timing까지 소유합니다.

RefactorBacklog:
- LootRewardPolicyBoundarySplit

리스크 / 후속:
- 이 항목은 P1입니다.
- 새 reward source, loot exclusion 변경, chest upgrade, world pickup UX 변경,
  loot table 확장 시 먼저 봐야 합니다.
- World pickup delivery는 InventoryTransferResponsibilitySplit과 겹칩니다.


Dialogue / NPC / Affection / Upgrade 리뷰

리뷰 범위:
- Dialogue playback과 blocker
- NPC feature handoff
- Merchant feature
- Upgrade feature
- Affection reward와 run modifier

핵심 결론:
- Dialogue playback과 dialogue input block의 owner는 DialogueService가 맞습니다.
- Dialogue 이후 stack UI를 여는 NPC feature는 dialogue blocker가 해제될 때까지
  기다려야 합니다.
- UpgradeManager는 책임이 과도하게 모여 있습니다.
- RunModifierService는 Upgrade 폴더 아래에 있지만 실제로는 system-wide service입니다.

구체 관찰:
- Merchant stock/session policy는 현재 구조상 당장 문제는 아닙니다.
- UpgradeManager는 progress, purchase, effect application, run-start effect,
  save request, UI flow, fade, input blocking을 함께 소유합니다.
- RunModifierService는 upgrade와 affection contributor를 모으고, loot, grave, chest,
  merchant, boss reward policy에서 소비됩니다.

RefactorBacklog:
- UpgradeRuntimeBoundarySplit
- RunModifierAggregationBoundarySplit

리스크 / 후속:
- RunModifierAggregationBoundarySplit은 P1입니다.
- 이미 reward와 progression 시스템들이 여기에 의존합니다.
- UpgradeRuntimeBoundarySplit은 P2입니다.
- 새 upgrade effect, run-start behavior, UI blocker, save timing을 수정할 때 시작하는
  것이 적절합니다.


Scene / Runtime Save 리뷰

리뷰 범위:
- ScenePortalTravelService
- GamePlayDataManager
- RunProgressCoordinator
- Player runtime capture / restore
- Save data와 run transition flow

핵심 결론:
- Scene travel, run-session pending state, player runtime restore, boss battle-end
  progress가 서로 가까워 ownership이 흐려질 수 있습니다.
- 현재 구조는 동작하지만, 향후 scene / save / run 변경 전에는 경계를 더 명확히
  해야 합니다.

RefactorBacklog:
- SceneRunStateBoundarySplit

리스크 / 후속:
- 이 항목은 P1입니다.
- scene/run/save 물리 재구성, 새 transition type, portal route 변경, boss battle-end
  변경, player runtime restore 작업 전에 먼저 봐야 합니다.
- 구현 시 portal travel, pending state consumption, boss reward/portal, run timer,
  save commit에 대한 play verification이 필요합니다.


Loading / Presentation / HUD 리뷰

리뷰 범위:
- Loading overlay
- Mouse cursor presentation
- Cinematic / display letterbox
- Status HUD tooltip / entry fallback
- Boss HUD dual / split health fallback

핵심 결론:
- Runtime-created UI / presentation은 prototype, debug fallback, emergency fallback으로는
  허용됩니다.
- Production-facing UI와 presentation은 scene 또는 prefab authored 구조가 맞습니다.
- Tooltip 내용처럼 동적으로 바뀌는 데이터는 괜찮습니다.
- 문제는 전체 visual template을 코드에서 생성하는 경우입니다.

RefactorBacklog:
- RuntimePresentationFallbackAuthoringSplit
- BossHudSpecialCaseSourceSplit

구체 관찰:
- Boss HUD common code가 현재 Slime Queen phase-two special source를 알고 있습니다.
- Slime Queen 예외 자체는 말단 특수 사례로 타당합니다.
- 다만 공용 HUD는 장기적으로 concrete boss type이 아니라 generic HUD snapshot/source를
  소비하는 방향이 낫습니다.

리스크 / 후속:
- RuntimePresentationFallbackAuthoringSplit은 UI/presentation polish 시 P2입니다.
- BossHudSpecialCaseSourceSplit은 다른 multi-body/shared-health boss가 추가되거나
  Boss HUD를 다시 작업하기 전까지 P3 watch item입니다.


Combat / Status 리뷰

리뷰 범위:
- Damage snapshot / element build-up flow
- ElementBuildUpResolver와 ElementOffenseSource
- Status HUD projection

핵심 결론:
- Element build-up에는 현재 두 개의 authoring/calculation path가 보입니다.
- DamageSnapshotBuilder는 elementBuildUps를 만들 수 있지만, CombatDamageAction은
  ElementOffenseSource에서 build-up을 중앙 계산합니다.
- 그래서 serialized per-hit/per-weapon element data가 실제로 작동하는 것처럼 보이지만
  apply path에서 무시될 수 있습니다.

RefactorBacklog:
- CombatElementBuildUpSourceUnification

리스크 / 후속:
- P2입니다.
- 다만 elemental weapon을 추가하거나 튜닝할 때는 중요도가 올라갑니다.
- 구현 전 DamagePayloadConfig.elementFormulas의 serialized 사용처를 audit해야 합니다.


Relic / Consumable 리뷰

리뷰 범위:
- RelicDefinition, RelicLogic, RelicInventory, RelicProcManager
- ConsumableDefinition, PlayerConsumableInventory

핵심 결론:
- RelicInventory는 크지만 현재는 domain aggregate로 허용 가능한 구조입니다.
- Relic proc 구조는 대체로 괜찮습니다.
- RelicLogic이 behavior를 만들거나 붙이고, RelicProcManager가 gameplay event를
  fan-out하는 구조입니다.
- Consumable 구조는 현재 단순 회복형 item 기준으로는 충분히 단순하고 괜찮습니다.

리스크 / 후속:
- RelicInventory는 단지 크다는 이유만으로 쪼개지 않는 편이 맞습니다.
- acquisition / delivery source가 더 늘거나 relic runtime state restore가 어려워지면
  다시 봅니다.
- Consumable은 conditional effect, multi-step effect, target 선택, long-running effect가
  들어올 때 별도 effect policy 분리를 검토합니다.

추천 사용 순서

- Inventory 또는 chest 작업을 한다면 InventoryTransferResponsibilitySplit부터 봅니다.

- UI 또는 presentation polish 작업을 한다면 RuntimePresentationFallbackAuthoringSplit부터 봅니다.
- Lock overlay refactor는 design rule이 결정되기 전까지 구현하지 않습니다.
